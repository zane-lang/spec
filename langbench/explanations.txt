# Notes on the results, one block per test, opened by "[test id]".
# Lines starting with '#' are comments; a blank line starts a new paragraph.
#
# A note may quote numbers only from the pinned run in
# langbench_results.json, and must be revised when a new run is pinned.
# The pinned run: 2026-10-07, a 13th Gen Intel Core i7-1355U laptop under
# WSL2, Zane compiler v0.7 with core v0.0, zane CLI v0.4, and the other
# compilers devbox.json pins. Run times are medians of five runs after one
# warmup. Build times come from one build per row.
#
# Cross-package optimization is enabled. Optimized CGT includes imported
# dependency bodies that plain CGT omits, so whole-tree loop counts cannot
# establish how much was evaluated at compile time. They are raw counts,
# not a folding score. This run does not include a before/after comparison
# with the old compiler or the old binary-tree representation.

[primes]
This fixed-bound sieve reads no input, so it is eligible for compile-time evaluation. The plain and optimized CGT each contain three loops, but the optimizer now includes imported dependency bodies; these counts alone do not establish what the executable computes at runtime.

The row medians range from 0.52 to 1.19 ms, with Zane at 0.68 ms. At this size, whole-process startup and timing variation prevent a useful ranking of sieve performance. The single build measurements are 0.785 s for Zane, 0.648 s and 0.886 s for plain and comptime C++, and 11.35 s and 14.13 s for plain and comptime Zig. Rust and D have lower measured build times for their comptime variants than for their plain ones; these single samples are not enough to establish a build-time advantage.

[trialdiv]
The count reads N, while its prime-table setup has a fixed bound. The whole-tree CGT loop counts do not identify how much of that setup was evaluated while compiling. Compiler v0.7 can evaluate and inline calls across core's package boundary, so those calls are no longer necessarily opaque.

Zane takes 1.173 s. C, C++, Rust, D and Zig take 0.374 to 0.380 s, and Go takes 0.601 s. Zane is 3.13 times the fastest row, C. These timings show the remaining gap, but do not identify which operations account for it.

[binarytrees]
This run measures the corrected reference-based Zane program. Each reference node owns its children, parent construction takes both children rather than deep-copying completed subtrees, and checking a tree borrows it. This matches the ownership transfer of child pointers in C++ and Rust more closely than the previous value-based program.

Zane takes 2.506 s, compared with 0.249 s for Go, 0.256 s for C, 0.335 s for C++ and 0.317 s for Rust. Zane is 10.07 times the fastest row and 7.48 times C++. Go leaves trees to its garbage collector, while C, C++ and Rust free them explicitly. Zane still performs allocation, traversal, scope-escape relocation and teardown; profiling is needed to attribute the remaining gap. This pinned run contains no old-representation control, so it cannot establish a before/after speedup on its own.

[mandelbrot]
The arithmetic workload uses no dynamic collections. Zane takes 0.479 s, compared with 0.427 s for C++, 0.428 s for C and 0.429 s for Rust. Go, D and Zig take 0.451 to 0.465 s. Zane is about 12% slower than the fastest row, C++.

Cross-package optimization now exposes core's arithmetic bodies to LLVM. This row no longer has the old explanation that every arithmetic operation must remain an out-of-line call into a separately compiled object. The timing alone does not explain the remaining difference.

[fannkuch]
C is fastest at 0.161 s; Go takes 0.162 s, D 0.170 s, Rust 0.178 s, C++ 0.191 s and Zig 0.232 s. Zane takes 1.067 s, 6.62 times C and 5.58 times C++.

The Zane program indexes and rewrites small lists in place. Its shape also differs: flips are counted by recursion and the next permutation is found in a bounded loop that returns early. Those source differences and the remaining list operations are candidates for investigation; this timing run does not isolate their costs. Core's index calls are now available to cross-package optimization.

[entities]
Each version stores entities inline and scans 96 MB of entity data. Zane takes 1.157 s, against 0.496 to 0.504 s for C, C++, Rust and D, 0.542 s for Zig and 0.621 s for Go. Zane is 2.33 times C++, the fastest row.

Allocation, initialization and scanning all contribute to the whole-process measurement. With core bodies now available to optimization, the remaining gap cannot be attributed just to unavoidable package-boundary calls without profiling.

[listgrowth]
Zane takes 0.814 s, within 1% of C++ at 0.807 s; their sample ranges overlap. It is faster than Go at 1.731 s and D at 1.670 s. C is fastest at 0.368 s, followed by Rust at 0.406 s and Zig at 0.542 s. Zane is 2.21 times C.

Each language grows its list by its own policy. Zane's backing store starts at a 128-byte block and doubles (memory.md §3.6); C doubles from four elements through realloc. The measurement includes both growth and the final sum, and does not separate allocation costs from indexing or arithmetic.

[ntree]
Rust is fastest at 0.293 s, followed by C at 0.439 s and Go at 0.493 s. C++ takes 0.708 s, Zig 0.743 s and D 1.263 s. Zane takes 3.823 s, 13.03 times Rust and 5.40 times C++.

Rust's Vec<Node> stores children inline, allocating once per internal node. The other versions allocate nodes separately and retain references or pointers to them, so the representations do different allocation work. Zane's nodes own lists of child references; constructing and dropping the tree includes both node and child-list storage. In Go and D the collector handles reclamation at times of its own choosing.

[treecopy]
Zane takes 1.490 s, compared with 0.233 s for Go, 0.259 s for C, 0.305 s for C++, 0.387 s for Rust and 0.392 s for D. Zig takes 0.293 s. Zane is 6.40 times Go, the fastest row, and 4.89 times C++.

Unlike binarytrees, this test deliberately retains value types and full-tree copying. A Zane value copy allocates every boxed payload afresh, so the two trees share nothing (memory.md §2.3); the other languages clone the tree as well. The original is read after the last copy, so replacing that copy with a move would change the workload. Allocation and deep-copy work remain even when calls across core's package boundary can be optimized.
