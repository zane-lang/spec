# Notes on the results, one block per test, opened by "[test id]".
# Lines starting with '#' are comments; a blank line starts a new paragraph.
#
# A note may quote numbers only from the pinned run in
# langbench_results.json, and must be revised when a new run is pinned.
# The pinned run: 2026-10-16, a 13th Gen Intel Core i7-1355U laptop under
# WSL2, Zane compiler v0.12 with core v0.1, zane CLI v0.6, and the other
# compilers devbox.json pins. Run times are medians of five runs after one
# warmup. Build times come from one build per row.
# Compiler commit: a490ae476163df4716eb0e94cd447b73b08fca8b.
#
# Optimized CGT includes imported dependency bodies that plain CGT omits, so
# whole-tree loop counts cannot establish how much was evaluated at compile
# time. They are raw counts, not a folding score.

[primes]
This fixed-bound sieve reads no input, so it is eligible for compile-time evaluation. The plain CGT contains three loops and the optimized CGT contains none. That shows loop elimination at the CGT stage, including the imported dependency bodies present in the optimized tree. It does not by itself establish that every operation was evaluated while compiling; the page therefore keeps the folding status as "not inferred".

The row medians range from 0.566 to 2.04 ms, with Zane at 0.566 ms. At this size, whole-process startup and timing variation prevent a useful ranking of sieve performance; Go's samples alone run from 1.23 to 3.79 ms. The single build measurements are 0.790 s for Zane, 0.413 s and 0.660 s for plain and comptime C++, and 12.74 s and 14.27 s for plain and comptime Zig. Rust's comptime variant has a lower measured build time than its plain one; one sample per row is not enough to establish a build-time advantage.

[trialdiv]
The count reads N, while its prime-table setup has a fixed bound. The whole-tree CGT loop counts do not identify how much of that setup was evaluated while compiling. The compiler can evaluate and inline calls across core's package boundary, so those calls are not necessarily opaque.

Zane takes 0.438 s. C is fastest at 0.403 s; D, Rust, C++ and Zig take 0.404 to 0.412 s, Go takes 0.635 s and OCaml 0.688 s. Zane takes 1.09 times as long as C and 1.08 times as long as C++. Its fastest sample, 0.433 s, is above the slowest sample of every row except Go and OCaml. These timings show the remaining gap, but do not identify which operations account for it.

[binarytrees]
This test measures a reference-based Zane program. Each reference node owns its children, parent construction takes both children rather than deep-copying completed subtrees, and checking a tree borrows it. This matches the ownership transfer of child pointers in C++ and Rust.

OCaml is fastest at 0.0554 s, and Zane follows at 0.0834 s. The rest are well behind: Go takes 0.259 s, C 0.273 s, Zig 0.324 s, Rust 0.335 s, C++ 0.356 s and D 0.403 s. Go, the next row after Zane, takes 3.10 times as long as Zane; C++ takes 4.27 times as long. Zane's slowest sample, 0.0836 s, is below the fastest of every row except OCaml.

OCaml allocates the short-lived trees in its minor heap and collects them generationally; Go and D leave trees to their garbage collectors, while C, C++, Rust and Zig free them explicitly. Zane uses scope-based storage and teardown. These are whole-program results for different allocation and reclamation strategies; they do not isolate the cost of allocating, traversing, relocating or dropping a node.

[mandelbrot]
The arithmetic workload uses no dynamic collections. Zane is fastest at 0.416 s, followed by Zig at 0.432 s and D at 0.433 s; C++, Go, C and Rust take 0.452 to 0.458 s, and OCaml 0.767 s. Zig takes 1.04 times as long as Zane and C++ takes 1.09 times as long. Zane's slowest sample, 0.420 s, is below every other row's fastest.

Optimized builds expose core's arithmetic bodies to LLVM, so arithmetic does not remain an out-of-line call into a separately compiled object. The timing alone does not explain why Zane leads; the programs are not identical in how they express the inner loop.

[fannkuch]
C is fastest at 0.159 s; Go takes 0.171 s, D 0.177 s, Rust 0.181 s and C++ 0.185 s. Zane takes 0.197 s, 1.24 times as long as C and 1.07 times as long as C++. It is faster than Zig at 0.239 s, and its samples overlap OCaml's, whose median is 0.204 s.

The Zane program indexes and rewrites small lists in place. Its shape also differs: flips are counted by recursion and the next permutation is found in a bounded loop that returns early. Those source differences and the remaining list operations are candidates for the gap; this timing run does not isolate their costs.

[entities]
Each version except OCaml stores entities inline and scans 96 MB of entity data. OCaml's array holds pointers to records, and a record mixing ints and floats boxes each float, so it reads more memory through more indirection. Zane is fastest at 0.465 s, followed by C++ at 0.518 s, Rust at 0.527 s and C at 0.531 s. D takes 0.542 s, Go 0.544 s, Zig 0.567 s and OCaml 1.11 s. C++ takes 1.11 times as long as Zane and C 1.14 times as long. Zane's samples run from 0.454 to 0.500 s, so its slowest overlaps C++'s fastest.

Allocation, initialization and scanning all contribute to the whole-process measurement, which does not separate them.

[listgrowth]
C is fastest at 0.379 s and Zane takes 0.398 s, 1.05 times as long; their sample ranges overlap. Rust follows at 0.428 s and Zig at 0.597 s. C++ takes 0.852 s, D 1.38 s, Go 1.81 s and OCaml 3.77 s.

Each language grows its list by its own policy. Zane's backing store starts at a 128-byte block and doubles (memory.md §3.6); C doubles from four elements through realloc. Each round reads only the final entity's hp and the list's size into a checksum; there is no full-list sum. The measurement includes appending, initialization, growth and teardown, and does not separate allocation costs from indexing or arithmetic.

[ntree]
Zane is fastest at 0.219 s, followed by Rust at 0.307 s, C at 0.450 s and Go at 0.493 s. C++ takes 0.736 s, Zig 0.843 s, D 1.30 s and OCaml 1.57 s. Rust takes 1.40 times as long as Zane and C++ takes 3.37 times as long. Zane's slowest sample, 0.226 s, is below every other row's fastest.

Rust's Vec<Node> stores children inline, allocating once per internal node. The other versions allocate nodes separately and retain references or pointers to them, so the representations do different allocation work. Zane's nodes own lists of child references; constructing and dropping the tree includes both node and child-list storage. In Go, D and OCaml the collector handles reclamation at times of its own choosing.

[treecopy]
Zane is fastest at 0.103 s, compared with 0.244 s for Go, 0.260 s for C, 0.307 s for Zig, 0.324 s for C++, 0.352 s for OCaml, 0.396 s for D and 0.442 s for Rust. Go takes 2.37 times as long as Zane and C++ takes 3.14 times as long. Zane's slowest sample, 0.107 s, is below every other row's fastest.

Unlike binarytrees, this test deliberately retains value types and full-tree copying. A Zane value copy allocates every boxed payload afresh, so the two trees share nothing (memory.md §2.3); the other languages clone the tree as well. The original is read after the last copy, so replacing that copy with a move would change the workload. Allocation and deep-copy work remain even when calls across core's package boundary can be optimized.

[nbody]
The five bodies' starting state is fixed and only the step count is read, so the setup is eligible for compile-time evaluation; the whole-tree CGT loop counts do not show how much of it was. Every version does the same floating-point operations in the same order and prints the same energies.

Zig is fastest at 0.140 s, well ahead of D at 0.187 s, C at 0.198 s and C++ at 0.200 s. Rust takes 0.216 s, OCaml 0.235 s, Zane 0.243 s and Go 0.310 s. Zane takes 1.23 times as long as C and 1.74 times as long as Zig, and its samples overlap OCaml's. The timing does not identify what Zig's build does differently in the pair loop, or where Zane's time goes.

[spectralnorm]
Zane, C++, Rust and C finish within 2% of each other, from 0.155 to 0.157 s, and Zane's samples overlap all three and D's, so this run does not rank them. Go and D take 0.164 s, Zig 0.204 s and OCaml 0.351 s. The work is a dense matrix-vector product whose entries are computed on the fly, so it is dominated by floating-point division and multiplication rather than by memory.

[allocfree]
Zane is fastest at 0.429 s, followed by Go at 0.598 s and D at 0.756 s. Zig takes 1.45 s, C++ 1.58 s, C 1.64 s, Rust 1.66 s and OCaml 1.98 s. Go takes 1.39 times as long as Zane and C 3.81 times as long. Zane's slowest sample, 0.432 s, is below every other row's fastest.

The random removal order frees a million small objects out of allocation order every round. C, C++ and Rust release each item through the C allocator and Zig through its smp_allocator as it is removed; Zane drops each removed item when its loop iteration ends. Go and D leave the items to their collectors, which reclaim them at times of their own choosing. OCaml's item record mixes ints and floats, so each item is three heap blocks, not one; that is how OCaml represents such a record, and the cost is part of its result. These are whole-program results for different allocators, and they do not separate allocation from release.

[gameloop]
C is fastest at 0.284 s, followed by Rust at 0.352 s, Go at 0.411 s and Zig at 0.453 s. C++ takes 1.23 s and Zane 1.38 s, 4.86 times as long as C and 1.12 times as long as C++; their sample ranges do not overlap. D takes 1.56 s, with one sample at 2.32 s, and OCaml 6.46 s.

Every version keeps the entities in spawn order and removes them from the front and the middle, so each removal shifts the entries behind it; about 1,860 entities are alive at the end. C moves those pointers with one memmove, while C++'s erase moves each unique_ptr in turn, clearing its source. The gap from C to C++, Zane and D follows the shift, but this run does not show which part of Zane's ordered remove accounts for its time.

[particles]
C, C++ and Zig are within 4% of each other at 0.133 to 0.138 s, and Go takes 0.147 s. Zane takes 0.179 s, 1.34 times as long as C, and its samples overlap Rust's, whose median is 0.181 s. D takes 0.226 s and OCaml 0.707 s.

Order does not matter here, so an expired particle's slot takes the last particle and no entries shift. About 1,160 particles are alive at the end. Each particle is its own object in every version, a reference type in Zane and a separate allocation elsewhere, so the run measures allocating, updating and releasing short-lived small objects; it does not separate the three.

[concscan]
Excluding OCaml, every row is within 11% of Zane, the fastest at 0.356 s: C++ and Go take 0.361 s, Rust 0.365 s, C 0.366 s, Zig 0.384 s and D 0.394 s. Zane's samples overlap C++'s, Go's and C's, so this run does not rank those four. OCaml takes 0.849 s; its array holds pointers to records, as in entities.

Each pass splits the inline entities into four shards and sums each on its own thread, 100 passes in all, and the measurement also includes building the entities. Zane spawns a call per shard, Go a goroutine, OCaml a domain and the others a thread. The close spread suggests the scan is bound by memory bandwidth rather than by how each language starts its threads, but this run does not measure either separately.
