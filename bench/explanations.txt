# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.txt).
#
# PROVENANCE AND NOISE. Measured on the maintainer's machine with the process
# pinned to four cores (taskset -c 0-3), so the four-worker pool in T8 and T12
# has real cores and those rows measure something. This machine is quiet by the
# standards of a shared container but not silent: across repeat runs of the same
# code the median row moved ~8%, three quarters stayed under ~10%, and the tail
# reached 30% or more (T4's inline scan moved 92% between two runs that did not
# touch it). Treat every absolute figure below as one run's median, good to about
# one significant figure. The durable content is the ratios, the orderings, and
# effects large enough to survive that band; where two rows fall inside it the
# note says they are a tie rather than picking a winner. Ratios taken *within* a
# single run are much steadier than absolute times across runs, so the notes lean
# on those.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Details:" note for its test. Some tests (T13, T14) are a compile-time
# A/B: the committed run is the default (global anchor pool) layout, and the
# note carries the comparison against the -DZM_INTERLEAVE build. Three
# default/interleaved pairs have been taken so far; all six A/B measurements
# favour the global pool, which is what the notes report, and none of them pins
# the magnitude.
#
# One caution specific to the committed pair: the interleaved run was taken on a
# quieter machine than its default partner. On the tests that mint no guests the
# two builds run identical code, and there the interleaved run came out ~24%
# faster — so its A/B numbers are biased *toward* the interleaved layout, and it
# lost anyway.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the committed
# zane_bench_results.txt. After editing them, rebuild the HTML with
#   python3 runbench.py --from-file
# which reuses that results file instead of re-running.

[Test 1]
Zane's fixed-region bump (~229us) is ~13x faster than malloc (~2.9ms) and
~1.6x faster than Pool (~362us). Zane's release is a no-op — the region
reclaims only when the scope drains — so its figure is allocation alone, where
malloc and Pool pay for both halves. The raw Arena baseline (~21us) is still
~11x quicker: Zane zero-writes a 4-byte backpointer per host and checks a
chunk boundary that Arena's flat frontier does not have. That is the honest
cost of a chunked region.

[Test 2]
Only the release loop is timed. These hosts provably never gain a guest, so
release does nothing at all: ~39ns for the whole 100k-object loop, about what
malloc spends freeing three of them. malloc (~1.3ms) and Pool (~278us) pay
real per-object cost — ~13ns and ~2.8ns each — because both must return a
block to a structure that later allocations search. A guested host pays more,
since its anchor is returned when its hosting identity ends (T10).

[Test 3]
With four interleaved sizes Zane (~389us) stays ~21x ahead of malloc (~8.0ms)
and ~7x ahead of Pool (~2.7ms): the fixed-size region has no size classes, so
mixed sizes are just more frontier bumps, at ~3.9ns apiece. Arena's bulk reset
(~75us) is the floor again, as in T1. Both competitors were unusually noisy in
this run — Pool's slowest pass ran 2.7x its fastest, and malloc's twice its
own — so read the ordering here, not the multiples.

[Test 4]
No allocation is timed — this is pure layout cost. Contiguous inline storage
(~75us) is the floor, with the chunked layouts close behind (UList ~83us,
CChunked ~88us). The scattered pointer array costs ~133us walked in order and
~194us shuffled, where the prefetcher can no longer hide the random hops. The
~2.6x spread between best and worst is the durable result; the gap between the
top three is not, and the inline row alone moved 92% between two runs that did
not touch it.

[Test 5]
Filling 100k 32-byte entities takes 13 in-place doublings from 128B up to a
full 1 MiB chunk, then two relocations into oversized spans copying 1 MiB and
2 MiB, because a block never grows across a chunk boundary (§3.6). At ~299us
Zane is level with C's realloc vector (~313us), which extends its mapping
instead of copying, and with CChunked (~320us) — all three inside the noise
band. Only UList (~1.12ms) is clearly behind. The copying is what bounding a
block to one chunk costs, and only the last two doublings pay it.

[Test 6]
The segmented tether adds one dependent load — the anchor cell — over a raw
pointer: ~117us baseline vs ~142us terminal resolve, about 1.21x. Spread over
100k accesses that is ~1.2ns against ~1.4ns each, so the extra load costs
about a quarter of a nanosecond and is largely hidden by the pipeline. That is
the terminal case only; T15 measures what an older identity pays. Whether the
chunk directory is register-cached or reloaded is inside the noise — the two
land within 1%.

[Test 7]
At steady-state churn Zane (~2.41ms) and Pool (~2.46ms) tie, with malloc
(~3.27ms) behind: per-frame update and simulation work dominate once entity
counts stabilize, and the raw allocation gaps from T1-T3 wash out. Zane also
holds the tightest range of the three across its 20 runs (~2.34-2.54ms), where
malloc's slowest pass is twice its fastest — with allocation no longer the
bottleneck, what is left to measure is how steady each one is.

[Test 8]
Under maximum churn Pool (~6.86ms) leads Zane (~7.70ms) and malloc (~8.11ms) —
an 18% field, where T1-T3 spanned more than an order of magnitude. The
work-stealing update variant is ~14x slower than plain Zane (~107ms) with four
real cores available, so it is not a pinning artifact: the per-frame particle
work is too small to amortize scheduling, and its ~78-151ms range across runs
is that scheduling jitter showing through.

[Test 9]
Only the refill is timed. Zane bumps the fixed-region frontier for the 50k new
objects (~92us, ~1.8ns each) and never touches the dead space Phase B left, so
fragmentation history is irrelevant to it. malloc (~1.12ms) and Pool (~574us)
refill from the freed slots and carry that history — roughly 12x and 6x
slower, at ~22ns and ~11ns an object. This is what the fixed-size region buys
by reclaiming nothing before the scope drains.

[Test 10]
Guest density barely registers: single root guest ~53us, no guests ~53us, one
guest per node ~56us. The last of those retires 4,000 payload anchors as their
hosting identities end, for ~5% over retiring none — anchors are never
enumerated, so the price is one backpointer test per node against an object
the post-order walk already has in cache. malloc's per-node free with
coalescing is ~98us (~1.8x slower); Pool (~54us) is level with Zane.

[Test 11]
The mixed workload compresses the field to a tie: Pool ~1.86ms, Zane ~1.91ms,
malloc ~2.04ms, a 9% span that sits inside the noise band. Updates, scans and
randomized maintenance dominate, so the allocator is only a small slice of the
total and none of the three separates from the others. Both regions run at
once here — entities bump and never come back, while the 128/256/512-byte list
blocks cycle through the exact-size stacks.

[Test 12]
Four read-only shards summed sequentially (~57us) and concurrently (~175us):
concurrency loses by 3x. With four cores actually available this is a real
result rather than a pinning artifact — spawning and joining the workers costs
~117us on top of work that takes 57us to do serially, so the shards are far
too small to repay the coordination. The concurrent row is also the least
repeatable here, ranging ~105-397us where the sequential one holds to
~57-71us. Both paths produce the asserted-identical total.

[Test 13]
Eight payload-only scans over 100k hosts at ~20% guest density: ~698us median,
~0.9ns per host per pass. The -DZM_INTERLEAVE build was slower in all three
pairs taken — by 0.1%, 5.1% and 10.9% — and in the committed pair it lost
despite running on a machine ~24% quicker on code the two builds share. The
direction is consistent across every pair; the magnitude is not, and the
smallest gap is inside the noise. T14 makes the weighting plainer.

[Test 14]
Ten payload scans per one tether-resolve pass: ~4.13ms median. The interleaved
build was slower in all three pairs — by 8.9%, 26.4% and 4.8% — and, as in
T13, its run in the committed pair had a ~24% machine advantage and still
lost. Six measurements in one direction is good evidence that protecting the
payload scan wins the aggregate; none pins the size, since this row has moved
31% between identical runs. Hence the design argument: scans are pervasive
where resolves are occasional, so the global pool wins here despite its dearer
resolve (T6).

[Test 15]
Each uncompressed hop costs about one more dependent anchor-cell load: ~164us
terminal, then ~316us, ~469us and ~802us at one, two and four hops.
Compressing as it resolves — the first of eight passes rewrites the tether,
the rest find it terminal — costs ~707us against a ~660us floor for the
terminal identity over identical structure, so it recovers about two thirds of
the four-hop penalty on the first repeated access (§4.8); the residual is its
store on every pass. That floor sits above the ~164us row on footprint, not
hops: a depth-4 chain is five hosts and five cells.

[Test 16]
A boxed payload takes size and alignment from its member's declared type, so
its stack is picked once (~623us for 60,000 alloc-and-release pairs); a
growable backing store looks its size up on every call (~657us). That ~6% is
the whole cost of not knowing a size until runtime (§3.2). Both pay a
pop-and-push that the frontier-only row (~60us) skips, and what it buys is
memory: frontier-only bumps through 17.9 MB of fresh chunks to hold a 1 MB
live set, where the stack runs recycle inside ~1.8 MB. Pool (~509us) leads on
raw-pointer links; malloc (~1.88ms) trails.

[Test 17]
Rehosting an 8,191-node boxed tree relocates every descendant recursively:
~42us with no guests, ~53us with a guest on every node. That ~27% is the
per-host anchor retarget, and it stays O(1) per host — no guest is ever
enumerated. The value side is the pair worth reading: deep-copying from an
existing place costs ~34us, constructing a fresh tree ~20us. Both are
O(structure), the content of §2.3, and the gap between them is the copy
proper, since a fresh result is built straight into its destination. malloc's
deep copy is ~125us, ~3.7x the value copy.
