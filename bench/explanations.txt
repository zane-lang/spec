# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.json, and zane_bench_results.txt rendered from it).
#
# PROVENANCE AND NOISE. The committed run is a fresh full-suite run, taken
# under WSL2 with no core pinning, on a hybrid CPU: 8 performance cores and
# 16 efficiency cores. That matters for the two rows that spawn threads, T8
# and T12, and for nothing else — see T12's note.
#
# Every row now carries all 20 per-run samples in zane_bench_results.json, so
# the spread below is checkable rather than asserted, and it shows two things.
# The first pass of a row is almost always its slowest, often by 3-5x, so a
# row's max is warm-up rather than variance. The median is taken over all 20
# samples, warm-up included; it is quoted here because it barely moves when
# that pass is dropped, not because the pass is excluded. T1's Zane row is
# 158.7us over all twenty and 152.8us over the last nineteen. And absolute
# figures move a great deal between runs of identical code: every row here
# came in 1.2-2.8x faster than the run before it. So treat each figure as one
# run's median, good to about one significant figure. The durable content is
# the ratios, the orderings, and effects large enough to survive that band;
# where two rows fall inside it the note says they tie rather than picking a
# winner, and where a finding did not survive the last re-run the note says
# that too.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Reading the result" note for its test — a section below that test's
# chart. It interprets the numbers; the configuration lives in the panel above
# the chart, and checked invariants live in that panel's meta rows. One test
# (T13) is a compile-time A/B against the -DZM_INTERLEAVE build. Those pairs
# predate this run, which is default-only: three have been taken, all three
# favour the global pool, and none of them pins the magnitude.
#
# One caution specific to those pairs: in one of them the interleaved run was
# taken on a quieter machine than its partner. On the tests that mint no
# guests the two builds run identical code, and there the interleaved run came
# out ~24% faster — so that pair's numbers are biased *toward* the interleaved
# layout, and it lost anyway.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the measurements in the
# committed zane_bench_results.json. After editing them, rebuild the page with
#   python3 runbench.py --from-file
# which re-renders from that file instead of measuring again.

[Test 1]
Zane's bump (~159us) runs ~13x faster than malloc (~2.06ms) and ~1.5x faster
than Pool (~231us) — and since only Zane's release is free, its figure is
allocation alone where the other two carry their frees inside it. Arena
(~14us) is a further ~11x ahead, but read that row for what it is rather than
as an allocator that beats this one: it bumps a pointer and never writes to
the memory it hands out, so it pays no cache-line fills at all. The row beside
it settles the point. The same flat arena writing one 4-byte field per object
costs ~155us, which is Zane's ~159us to within 2%. Nothing separating those
two is the chunked design; what separates either of them from the pure bump is
the cache-line fills that one write pulls in across ~4 MB, and every allocator
that initializes an object pays those. What the pure-bump row marks is the
floor for address arithmetic, and that is a floor no allocator which
initializes anything can reach.

[Test 2]
Zane's row is not a fast release loop; it is no loop at all. zm_host_release
is an empty function, so the compiler deletes the 100k-iteration loop outright,
and the harness reports the row as eliminated rather than timing two
timestamps around nothing. malloc (~959us) and Pool (~194us) spend ~9.6ns and
~1.9ns an object returning blocks to a structure that later allocations must
search. Shuffling costs them nothing extra; having the structure at all is the
cost.

[Test 3]
Mixed sizes cost Zane nothing structural: ~260us, ~2.6ns a block, and the
ordering against malloc (~3.51ms, ~13x) and Pool (~980us, ~3.8x) is what T1
already showed at a single size. Arena (~29us) is again the floor. The
multiples are the part to distrust — the previous run put malloc at ~21x and
Pool at ~7x on this same code, both competitors having been unusually slow
that day. The ordering is what has held across both.

[Test 4]
Layout alone spans ~3.2x. Contiguous inline storage (~33us) is the floor, the
chunked forms sit close behind (UList ~47us, CChunked ~51us), and the
scattered pointer array costs ~106us. What did not survive the re-run is the
shuffle: walking the pointer array in order (~106us) and shuffled (~101us) now
tie, where the previous run had the shuffled walk costing ~1.5x the sequential
one. Whatever separated them there did not reproduce here, so treat the
prefetcher story that reading invited as unsupported. The gap between
contiguous storage and any scattered form is what both runs agree on.

[Test 5]
Copying costs Zane nothing measurable, and this run puts it in front: ~162us
against C's realloc vector (~224us), which extends its mapping instead of
copying, and CChunked (~204us). The previous run had those three inside each
other's noise, so read the ~1.3x lead as "not behind" rather than as a win.
Only UList (~749us) is clearly last, in both runs. Bounding a block to one
chunk is what forces the relocations, and it stays cheap because only the two
oversized spans copy at all; growth at the frontier moves nothing.

[Test 6]
The extra dependent load costs ~1.24x: ~84us direct against ~104us tethered,
about a fifth of a nanosecond on each of 100k accesses, most of it absorbed by
the pipeline. Caching the chunk directory or re-fetching it lands within ~3%
— inside the noise, so the directory is not on the critical path. This is the
terminal case only; T14 measures what an identity that has outlived a move
pays.

[Test 7]
Once entity counts stabilize the allocator stops mattering: Zane (~1.19ms)
and Pool (~1.18ms) tie, malloc (~1.39ms) trails by ~18%, and the
order-of-magnitude gaps of T1-T3 have gone into per-frame update work. All
three are steady here, each holding within 1.2-1.4x across its 20 passes. The
erratic malloc the previous run reported — its slowest pass twice its fastest
— did not reproduce, so steadiness is no longer what separates them.

[Test 8]
Maximum churn narrows the field rather than widening it: Pool (~3.49ms), Zane
(~3.70ms) and malloc (~3.99ms) span 14%, against an order of magnitude in
T1-T3. The work-stealing row is the result worth keeping — ~23.6ms, ~6.4x
plain Zane, with the pool already warm, so startup does not explain it.
Per-frame particle work is too small to amortize scheduling. The multiple is
softer than the ~14x the previous run reported and the row is far steadier
here (~22.9-29.2ms against ~78-151ms), but both runs say the same thing:
distributing this much work costs several times more than doing it.

[Test 9]
A bump frontier cannot be fragmented, and the refill shows it: Zane takes
~77us for the 50k objects, ~1.5ns each, the rate it would charge on an
untouched region — and it holds that rate across all 20 passes. The
competitors do not, which is the part the per-run samples now make visible.
malloc (~852us) and Pool (~346us) refill from the freed slots at ~17ns and
~7ns an object, ~11x and ~4.5x, and both degrade as the run proceeds: malloc's
passes climb from ~480us to ~890us and Pool's from ~81us to ~474us before
plateauing, each cycle handing the free list back in a worse order than it
found it. Zane's flat line against those two curves is what reclaiming nothing
until the scope drains buys.

[Test 10]
Read the ratios here, not the absolutes, and read the guest-density rows with
care. These figures were measured before build_tree was fixed, when the first
child of every node took the whole node budget and each later sibling was
NULL — a 4,000-node chain of depth 3,999 with no branch points, rather than a
branching tree. What survives is the comparison against the other allocators,
since every row ran on that same shape: malloc's coalescing costs ~2.4x
Zane's teardown and Pool (~36us) ties it, and a check on the corrected
topology reproduced both. What does not survive is the reading that guest
density is free. These numbers put the fully guested row nominally fastest of
the three, which the chain produced; on a real branching tree the same check
put it a few percent behind, in line with the ~5% an earlier run reported.
The mechanism is what makes the cost small either way: anchors are never
enumerated, so retiring 4,000 payload anchors is one backpointer test per
node, against an object the post-order walk already holds in cache. Teardown
scales with the tree, not with how much of it is guested — but the figures
above need a re-run before they say so.

[Test 11]
The mixed workload compresses the field to a tie, and the previous run's
caution proved right: Zane ~1.35ms, Pool ~1.40ms, malloc ~1.47ms, where that
run had Pool in front of Zane. Updates, scans and randomized maintenance
dominate, so the allocator is only a small slice of the total. The 9% between
fastest and slowest is inside what a median shifts between runs, and the
ordering duly moved.

[Test 12]
Concurrency loses, and by how much depends on where the four workers land.
The scan splits into four equal shards and waits for all of them, so a pass
runs at the speed of its slowest shard — and on a hybrid host with 8
performance cores against 16 efficiency ones, nothing pins a worker to
either. The 20 passes spread 4.5x accordingly: ~72us at best, ~194us median,
~322us at worst, against ~24us sequential. The best pass is the one to read.
At ~2.9x sequential it reproduces the ~3.1x an earlier run measured with the
process pinned to four cores, so the ~7.9x median is core placement, not the
cost of distributing. The finding survives either reading: distributing a
24us scan costs several times more than doing it outright, because per-shard
work this small cannot amortize the handoff. T8 shows the other side of the
same coin — at ~23ms a pass its work-stealing row spreads only 1.28x, both
because the work amortizes placement and because stealing lets a fast core
drain a slow one's queue.

[Test 13]
~3.57ms for the weighted mix. The A/B evidence predates this run, which is
default-only: across three default/interleaved pairs the interleaved build
lost every one — by 8.9%, 26.4% and 4.8% — one of them from a ~24% machine
advantage. Three measurements in one direction is reasonable evidence that
protecting the scan wins the aggregate; none pins its size. A payload-only
companion agreed on all three pairs before it was retired as redundant with
this test, which weights the same effect properly. The design argument
follows: scans are pervasive and un-hoistable where resolves are occasional,
so the pool's dearer resolve (T6) is the right trade.

[Test 14]
Hops are linear and expensive: ~124us, ~212us, ~333us and ~605us at zero,
one, two and four. Compression costs ~357us against the ~298us floor,
recovering about four fifths of the four-hop penalty on the very first
repeated access — what §4.8 claims for it — and the ~59us residual is the
store it makes on every pass. The floor is the figure to notice: it sits ~2.4x
above the ~124us terminal row on footprint alone, five hosts and five cells
against one.

[Test 15]
Not knowing a size until runtime costs nothing measurable: ~237us for the
runtime size class against ~242us for the static one over 60,000 pairs, the
runtime row nominally ahead. The previous run put the static row ~6% in front.
The effect is inside the noise in both and this run reverses its sign, so the
honest reading is that a runtime size class is free, not that it is cheap. The
stacks cost far more — the frontier-only row runs ~50us, ~4.8x under both —
and what they buy is memory rather than time: frontier-only bumps through
17.9 MB of fresh chunks to hold a 1 MB live set where the stack runs recycle
inside ~1.8 MB. Pool (~212us) stays ahead by ~1.1x because its link is a raw
pointer where §3.1 makes this one a segmented offset: inherent, not
recoverable.

[Test 16]
Guesting every node costs rehosting ~28% — ~42us against ~33us — and no more,
because each host retargets its own anchor and no guest is ever enumerated.
That is the steadiest figure in the suite, the previous run having put it at
~27%. The value pair is the one to read: ~18us to deep-copy from an existing
place against ~12us to construct fresh. Both are O(structure) as §2.3
requires, and the ~5us between them is the copy itself, which is why only an
existing source pays it. malloc's deep copy is ~95us, ~5.4x.
