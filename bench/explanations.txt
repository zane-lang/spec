# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.txt), measured in a shared cloud container rather than on
# dedicated hardware. That environment is noisy: the max columns in the results
# file run far above the medians on several tests, and the two thread-pool
# tests (T8, T12) are dominated by contention for a small, shared core budget.
# The notes therefore lean on relative ordering and on the large, repeatable
# effects, not on close calls between adjacent numbers.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Details:" note for its test.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the committed
# zane_bench_results.txt. After editing them, rebuild the HTML with
#   python3 runbench.py --from-file
# which reuses that results file instead of re-running.

[Test 1]
Zane's bump-arena alloc (~125us median) comes in ~29x faster than malloc
(~3.65ms) and ~4.5x faster than Pool (~562us). The raw Arena baseline (~63us)
is still about 2x quicker, which is the harness's own per-object bookkeeping
rather than anything the memory model requires: objects carry no per-instance
metadata at all now that hosted objects are never relocated.

[Test 2]
Only the free loop is timed. Zane's frees are no-ops, so it finishes in ~0.06us
— effectively unmeasurable — while malloc (~7.40ms) and Pool (~1.17ms) pay real
per-object cost. This is the bulk-reclaim model at its most extreme: nothing is
returned per object, so free order cannot matter.

[Test 3]
With four interleaved sizes Zane (~1.10ms) stays ~10.6x ahead of malloc
(~11.70ms) and ~2.3x ahead of Pool (~2.56ms): the bump arena has no size
classes, so mixed sizes are just more frontier bumps. The raw Arena baseline
(~121us) leads by ~9x on the harness's own per-object bookkeeping.

[Test 4]
No allocation is timed here — this is pure layout cost. Contiguous inline
storage (~126us) is the floor; the chunked layouts stay close on locality
(CChunked ~136us, UList ~148us) while the pointer arrays pay for the chase
(~225us sequential, ~287us shuffled). This is the test that pays for keeping
fields inline: a densely packed run of objects beats a run of references by
roughly 1.8x sequentially and 2.3x once access order is scrambled.

[Test 5]
Growing an owned buffer in place (~148us) beats C's realloc vector (~445us) by
~3x and the never-copy chunked forms by more (CChunked ~663us, UList ~1.26ms).
The in-place path wins because the buffer is the dynamic frontier allocation,
so growth is a frontier bump rather than an allocate-and-copy.

[Test 6]
A guest is a u32 segmented offset naming the object's storage directly, so a
deref is one chunk-directory lookup and then the field — no indirection cell,
because a hosted object never moves. That lands it at parity with a raw pointer
chase: ~154us cached and ~144us reloaded against a ~160us direct-pointer
baseline. Both paths do two loads (array slot then object, or directory entry
then object) and the directory stays hot, so the difference is inside this
environment's noise. Whether the chunk directory is register-cached or reloaded
is likewise not separable here.

[Test 7]
At steady-state churn the allocators sit close (Zane ~4.36ms, Pool ~4.44ms,
malloc ~4.85ms): once entity counts stabilize, per-frame update and simulation
work dominate and the raw allocation gaps from Tests 1-3 mostly wash out.

[Test 8]
Sequential Zane (~14.42ms), Pool (~14.40ms), and malloc (~14.85ms) tie, for the
same reason as T7 — the per-frame update dominates. The work-stealing variant
(~79.74ms) is ~5.5x *slower* than sequential, which is an artifact of the
environment rather than of the model: this container has few schedulable cores,
so pool coordination costs more than the parallel update saves.

[Test 9]
Refilling a checkerboard-fragmented heap is where bulk reclaim shows its
widest margin. Zane refills in ~33us because the arena never fragmented — the
frontier simply advances and the freed evens are irrelevant. malloc (~2.96ms)
and Pool (~1.24ms) refill from the slots freed in Phase B and carry that
history: roughly 90x and 38x slower.

[Test 10]
All three Zane variants land together (~49-56us) because arena teardown does no
per-node free work — the timed cost is just the post-order walk, and the guest
count does not move it, since a guest is a u32 copied from the host with no cell
to mint. malloc's per-node free with coalescing is ~201us (~3.8x slower) and
Pool is ~96us.

[Test 11]
The mixed workload compresses the field (Zane ~3.00ms, malloc ~3.38ms, Pool
~3.10ms): updates, scans, and randomized maintenance dominate the time, so the
allocator strategy is only a small slice of the total — the expected outcome for
a realistic churn pattern.

[Test 12]
Four read-only shards summed sequentially (~114us) beat the concurrent run
(~245us) on this machine. As in T8, that inversion is the environment: the shard
work is small and the container's core budget is contended, so pool
coordination costs more than the parallelism returns. Both produce the
asserted-identical total, which is the correctness point of the test.
