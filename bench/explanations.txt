# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.txt).
#
# PROVENANCE AND NOISE. Measured on the maintainer's machine with the process
# pinned to four cores (taskset -c 0-3), so the four-worker pool in T8 and T12
# has real cores and those rows measure something. This machine is quiet by the
# standards of a shared container but not silent: across repeat runs of the same
# code the median row moved ~8%, three quarters stayed under ~10%, and the tail
# reached 30% or more (T4's inline scan moved 92% between two runs that did not
# touch it). Treat every absolute figure below as one run's median, good to about
# one significant figure. The durable content is the ratios, the orderings, and
# effects large enough to survive that band; where two rows fall inside it the
# note says they are a tie rather than picking a winner. Ratios taken *within* a
# single run are much steadier than absolute times across runs, so the notes lean
# on those.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Details:" note for its test. Some tests (T13, T14) are a compile-time
# A/B: the committed run is the default (global anchor pool) layout, and the
# note carries the comparison against the -DZM_INTERLEAVE build. Three
# default/interleaved pairs have been taken so far; all six A/B measurements
# favour the global pool, which is what the notes report, and none of them pins
# the magnitude.
#
# One caution specific to the committed pair: the interleaved run was taken on a
# quieter machine than its default partner. On the tests that mint no guests the
# two builds run identical code, and there the interleaved run came out ~24%
# faster — so its A/B numbers are biased *toward* the interleaved layout, and it
# lost anyway.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the committed
# zane_bench_results.txt. After editing them, rebuild the HTML with
#   python3 runbench.py --from-file
# which reuses that results file instead of re-running.

[Test 1]
Zane's bump (~229us) runs ~13x faster than malloc (~2.9ms) and ~1.6x faster
than Pool (~362us) — and since only Zane's release is free, its figure is
allocation alone where the other two carry their frees inside it. Arena
(~21us) is a further ~11x ahead, and that gap is the whole price of the
chunked design: a per-host backpointer write, plus the chunk-boundary check a
flat frontier never makes.

[Test 2]
The whole 100k-object release loop measures ~39ns — three malloc frees' worth,
for a hundred thousand objects — so what this row shows is not a fast release
path but the absence of one. malloc (~1.3ms) and Pool (~278us) spend ~13ns and
~2.8ns an object returning blocks to a structure that later allocations must
search. Shuffling costs them nothing extra; having the structure at all is the
cost.

[Test 3]
Mixed sizes cost Zane nothing structural: ~389us, ~3.9ns a block, and the
ordering against malloc (~8.0ms, ~21x) and Pool (~2.7ms, ~7x) is what T1
already showed at a single size. Arena (~75us) is again the floor. Read the
ordering rather than the multiples here — both competitors were unusually
noisy, malloc spanning 2.0x and Pool 2.7x between their own fastest and
slowest passes.

[Test 4]
Layout alone spans ~2.6x. Contiguous inline storage (~75us) is the floor, the
chunked forms sit close behind (UList ~83us, CChunked ~88us), and the
scattered pointer array costs ~133us walked in order, ~194us shuffled, once
the prefetcher can no longer hide the hops. Only that spread is durable: the
top three are separated by less than this test's own movement between runs,
the inline row having shifted 92% between two that did not touch it.

[Test 5]
Copying costs Zane nothing measurable: at ~299us it ties C's realloc vector
(~313us), which extends its mapping instead of copying, and CChunked (~320us)
— the three are inside the noise of each other. Only UList (~1.12ms) is
clearly behind. Bounding a block to one chunk is what forces the relocations,
and it stays cheap because only the two oversized spans copy at all; growth at
the frontier moves nothing.

[Test 6]
The extra dependent load costs ~1.21x: ~117us direct against ~142us tethered,
about a quarter of a nanosecond on each of 100k accesses, most of it absorbed
by the pipeline. Caching the chunk directory or re-fetching it lands within 1%
— inside the noise, so the directory is not on the critical path. This is the
terminal case only; T15 measures what an identity that has outlived a move
pays.

[Test 7]
Once entity counts stabilize the allocator stops mattering: Zane (~2.41ms) and
Pool (~2.46ms) tie, malloc (~3.27ms) trails by a third, and the
order-of-magnitude gaps of T1-T3 have gone into per-frame update work.
Steadiness is what separates them instead — Zane holds ~2.34-2.54ms across its
20 runs where malloc's slowest pass is twice its fastest, so malloc's cost is
erratic as well as higher.

[Test 8]
Maximum churn narrows the field rather than widening it: Pool (~6.86ms), Zane
(~7.70ms) and malloc (~8.11ms) span 18%, against an order of magnitude in
T1-T3. The work-stealing row is the result worth keeping — ~107ms, ~14x plain
Zane, on four real cores with the pool already warm, so neither pinning nor
startup explains it. Per-frame particle work is too small to amortize
scheduling, and its ~78-151ms range is that jitter.

[Test 9]
A bump frontier cannot be fragmented, and the refill shows it: Zane takes
~92us for the 50k objects, ~1.8ns each, the rate it would charge on an
untouched region. malloc (~1.12ms) and Pool (~574us) refill from the freed
slots and so carry phase B's history with them, at ~22ns and ~11ns an object —
~12x and ~6x. That is what reclaiming nothing until the scope drains buys,
measured against allocators that must.

[Test 10]
Guest density barely registers: ~53us with none, ~53us with a single root
guest, ~56us with one per node. Retiring 4,000 payload anchors therefore costs
~5%, because anchors are never enumerated — the price is one backpointer test
per node, against an object the post-order walk already holds in cache.
malloc's coalescing puts it at ~98us, ~1.8x; Pool (~54us) ties Zane. Teardown
scales with the tree, not with how much of it is guested.

[Test 11]
The mixed workload compresses the field to a tie: Pool ~1.86ms, Zane ~1.91ms,
malloc ~2.04ms. Updates, scans and randomized maintenance dominate, so the
allocator is only a small slice of the total. Within one run the rows barely
move — this is the steadiest multi-row test in the suite — but the 9% between
them is inside the ~8-10% a median shifts across runs, so the ordering is not
durable.

[Test 12]
Concurrency loses by 3x: ~57us sequential against ~175us on four workers. With
the pool pre-warmed and four real cores this is a genuine result rather than
startup cost — the ~117us difference is spent coordinating work that takes
57us to do outright. It is also much the least repeatable row here, ranging
~105-397us where the sequential row holds to ~57-71us, which is contention
showing rather than computation.

[Test 13]
~698us for eight passes, ~0.9ns per host per pass. The interleaved build lost
all three pairs — by 0.1%, 5.1% and 10.9% — and lost the committed one from a
~24% machine advantage on code the two builds share. The direction is
consistent; the magnitude is not, and the narrowest gap would be noise on its
own. A payload-only scan is where the global pool should look best, since
interleaving puts cells in a stream this test never reads. T14 weights it
properly.

[Test 14]
~4.13ms for the weighted mix. The interleaved build lost all three pairs — by
8.9%, 26.4% and 4.8% — the committed one from a ~24% machine advantage. Six
measurements in one direction is good evidence that protecting the scan wins
the aggregate; none pins its size, this row having moved 31% between identical
runs. The design argument follows: scans are pervasive and un-hoistable where
resolves are occasional, so the pool's dearer resolve (T6) is the right trade.

[Test 15]
Hops are linear and expensive: ~164us, ~316us, ~469us and ~802us at zero, one,
two and four. Compression costs ~707us against the ~660us floor, recovering
about two thirds of the four-hop penalty on the very first repeated access —
what §4.8 claims for it — and the ~47us residual is the store it makes on
every pass. The floor is the figure to notice: it sits ~4x above the ~164us
terminal row on footprint alone, five hosts and five cells against one.

[Test 16]
Not knowing a size until runtime costs ~6%: ~623us against ~657us over 60,000
pairs. The stacks cost far more — the frontier-only row runs ~60us, an order
of magnitude under both — and what they buy is memory rather than time:
frontier-only bumps through 17.9 MB of fresh chunks to hold a 1 MB live set
where the stack runs recycle inside ~1.8 MB. Pool (~509us) stays ahead because
its link is a raw pointer where §3.1 makes this one a segmented offset:
inherent, not recoverable.

[Test 17]
Guesting every node costs rehosting ~27% — ~42us against ~53us — and no more,
because each host retargets its own anchor and no guest is ever enumerated.
The value pair is the one to read: ~34us to deep-copy from an existing place
against ~20us to construct fresh. Both are O(structure) as §2.3 requires, and
the ~14us between them is the copy itself, which is why only an existing
source pays it. malloc's deep copy is ~125us, ~3.7x.
