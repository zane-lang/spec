# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.txt).
#
# PROVENANCE AND NOISE. Measured on the maintainer's machine with the process
# pinned to four cores (taskset -c 0-3), so the four-worker pool in T8 and T12
# has real cores and those rows measure something. This machine is quiet by the
# standards of a shared container but not silent: across repeat runs of the same
# code the median row moved ~8%, three quarters stayed under ~10%, and the tail
# reached 30% or more (T4's inline scan moved 92% between two runs that did not
# touch it). Treat every absolute figure below as one run's median, good to about
# one significant figure. The durable content is the ratios, the orderings, and
# effects large enough to survive that band; where two rows fall inside it the
# note says they are a tie rather than picking a winner. Ratios taken *within* a
# single run are much steadier than absolute times across runs, so the notes lean
# on those.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Details:" note for its test. Some tests (T13, T14) are a compile-time
# A/B: the committed run is the default (global anchor pool) layout, and the
# note carries the comparison against the -DZM_INTERLEAVE build. Three
# default/interleaved pairs have been taken so far; all six A/B measurements
# favour the global pool, which is what the notes report, and none of them pins
# the magnitude.
#
# One caution specific to the committed pair: the interleaved run was taken on a
# quieter machine than its default partner. On the tests that mint no guests the
# two builds run identical code, and there the interleaved run came out ~24%
# faster — so its A/B numbers are biased *toward* the interleaved layout, and it
# lost anyway.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the committed
# zane_bench_results.txt. After editing them, rebuild the HTML with
#   python3 runbench.py --from-file
# which reuses that results file instead of re-running.

[Test 1]
Zane's fixed-region bump (~229us) is ~13x faster than malloc (~2.9ms) and ~1.6x
faster than Pool (~362us). The raw Arena baseline (~21us) is still an order of
magnitude quicker: Zane zero-writes a 4-byte backpointer per host and checks a
chunk boundary that Arena's flat frontier does not have. That is the honest
cost of a chunked region.

[Test 2]
Only the release loop is timed. These hosts provably never gain a guest, so
release does nothing at all — ~0.04us, effectively unmeasurable — while malloc
(~1.3ms) and Pool (~278us) pay real per-object cost. A guested host pays more,
since its anchor is returned when its hosting identity ends (T10).

[Test 3]
With four interleaved sizes Zane (~389us) stays ~21x ahead of malloc (~8.0ms)
and ~7x ahead of Pool (~2.7ms): the fixed-size region has no size classes, so
mixed sizes are just more frontier bumps. Both competitors were unusually slow
in this run, so read the ordering, not the multiples.

[Test 4]
No allocation is timed — this is pure layout cost. Contiguous inline storage
(~75us) is the floor, with the chunked layouts close behind (UList ~83us,
CChunked ~88us). The scattered pointer array costs ~133us walked in order and
~194us shuffled, where the prefetcher can no longer hide the random hops. The
~2.6x spread between best and worst is the durable result; the gap between the
top three is not.

[Test 5]
Filling 100k 32-byte entities takes 13 in-place doublings from 128B up to a
full 1 MiB chunk, then two relocations into oversized spans copying 1 MiB and 2
MiB, because a block never grows across a chunk boundary (§3.6). At ~299us Zane
is level with C's realloc vector (~313us), which extends its mapping instead of
copying; the 4% margin is inside the noise. Both beat the never-copy chunked
forms (CChunked ~320us, UList ~1.12ms). That copying is the price of bounding a
block to one chunk, and only the last two doublings pay it.

[Test 6]
The segmented tether adds one dependent load — the anchor cell — over a raw
pointer: ~117us baseline vs ~142us terminal resolve, about 1.21x. That is the
terminal case only; T15 measures what an older identity pays. Whether the chunk
directory is register-cached or reloaded is inside the noise — the two land
within 1%.

[Test 7]
At steady-state churn Zane (~2.41ms) and Pool (~2.46ms) tie, with malloc
(~3.27ms) behind: per-frame update and simulation work dominate once entity
counts stabilize, and the raw allocation gaps from T1-T3 wash out.

[Test 8]
Under maximum churn Pool (~6.86ms) leads Zane (~7.70ms) and malloc (~8.11ms).
The work-stealing update variant is more than an order of magnitude slower
(~107ms) with four real cores available, so it is not a pinning artifact: the
per-frame particle work is too small to amortize scheduling.

[Test 9]
Only the refill is timed. Zane bumps the fixed-region frontier for the 50k new
objects (~92us) and never touches the dead space Phase B left, so fragmentation
history is irrelevant to it. malloc (~1.12ms) and Pool (~574us) refill from the
freed slots and carry that history — roughly 12x and 6x slower. This is what
the fixed-size region buys by reclaiming nothing before the scope drains.

[Test 10]
Guest density barely registers: single root guest ~53us, no guests ~53us, one
guest per node ~56us. The last of those retires 4,000 payload anchors as their
hosting identities end, for ~5% over retiring none — anchors are never
enumerated, so the price is one backpointer test per node against an object the
post-order walk already has in cache. malloc's per-node free with coalescing is
~98us (~1.8x slower); Pool (~54us) is level with Zane.

[Test 11]
The mixed workload compresses the field (Pool ~1.86ms, Zane ~1.91ms, malloc
~2.04ms): updates, scans and randomized maintenance dominate, so the allocator
is only a small slice of the total and Zane and Pool are indistinguishable.
Both regions run at once here — entities bump and never come back, while the
128/256/512-byte list blocks cycle through the exact-size stacks.

[Test 12]
Four read-only shards summed sequentially (~57us) and concurrently (~175us):
concurrency loses by 3x. With four cores actually available this is a real
result rather than a pinning artifact — the shard work is small enough that
coordination costs more than the parallelism returns. Both paths produce the
asserted-identical total.

[Test 13]
Eight payload-only scans over 100k hosts at ~20% guest density: ~698us median.
The -DZM_INTERLEAVE build was slower in all three pairs taken — by 0.1%, 5.1%
and 10.9% — and in the committed pair it lost despite running on a machine ~24%
quicker on code the two builds share. The direction is consistent; the
magnitude is not. T14 is where the weighting makes it plainer.

[Test 14]
Ten payload scans per one tether-resolve pass: ~4.13ms median. The interleaved
build was slower in all three pairs — by 8.9%, 26.4% and 4.8% — and, as in T13,
the committed pair's interleaved run had a ~24% machine advantage and still
lost. Six measurements all in one direction is good evidence that protecting
the payload scan wins the aggregate; none pins the size, since this row has
moved 31% between runs of identical code. That is the design argument:
pervasive scans are common and un-hoistable while resolves are occasional, so
the global pool should win here even though its individual resolve is dearer
(T6).

[Test 15]
Each uncompressed hop costs about one more dependent anchor-cell load: ~164us
terminal, ~316us at one hop, ~469us at two, ~802us at four. Compressing as it
resolves — the first of eight passes walks the chain and rewrites the tether,
the other seven find it terminal — costs ~707us against a ~660us floor for
resolving the terminal identity directly over the identical structure. So
compression recovers about two thirds of the four-hop penalty on the very first
repeated access, which is what §4.8 claims for it, and the residual is the
store it does on every pass. The gap between that ~660us floor and the ~164us
terminal-anchor row is not hops but footprint: a depth-4 chain is five hosts
and five cells. The test also asserts what it cannot time — a compressed tether
is exactly the chain's terminal identity, and a depth-4 chain allocates exactly
five cells for four forwarding edges, so merging two anchored identities
allocates none (§4.2).

[Test 16]
The two kinds of dynamic block in §3.2 differ by the cost of not knowing a size
until runtime: a boxed payload takes size and alignment from the member's
declared type, so its stack is picked once (~623us for 60,000 alloc-and-release
pairs, about 10ns a pair), while a growable backing store's size is a runtime
value looked up on each call (~657us). That ~6% is all the lookup costs. Both
then pay the pop-and-push, which is what separates them from the frontier-only
row (~60us, about 1ns a pair) — and that row is what the fixed-size region
does, faster per operation but never reusing a byte. What the stacks buy is the
memory: the frontier-only run bumps through 17.9 MB of fresh chunks to hold a 1
MB live set, while the stack runs recycle inside ~1.8 MB. Pool's free list
(~509us) stays ahead of both because a link there is a raw pointer, where §3.1
makes one here a segmented offset resolved through the chunk directory —
inherent to the addressing, not recoverable. malloc (~1.88ms) is far behind
either way. The assertions carry as much as the timings: a freed block comes
back for a request of the same byte size and alignment, and is withheld from
one that differs in either.

[Test 17]
Rehosting an 8,191-node boxed tree relocates every descendant recursively:
~42us with no guests, ~53us with a guest on every node. That ~27% is the per-
host anchor retarget, and it stays O(1) per host — no guest is ever enumerated.
The value side is the pair worth reading: deep-copying from an existing place
costs ~34us, constructing a fresh tree ~20us. Both are O(structure), which is
the content of §2.3, and the gap between them is the copy proper, since a fresh
non-place result is built directly in its destination. That is why only an
existing source pays. Relocation costs more than the copy because a hosted node
is 24 bytes to the value node's 16 and each old block is returned to its stack
on the way. malloc's equivalent deep copy is ~125us, ~3.7x the value copy.
