# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.txt), measured in a shared cloud container rather than on
# dedicated hardware. That environment is noisy: the max columns in the results
# file run far above the medians on several tests, and the two thread-pool
# tests (T8, T12) are dominated by contention for a small, shared core budget.
# The notes therefore lean on relative ordering and on the large, repeatable
# effects, not on close calls between adjacent numbers.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Details:" note for its test.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the committed
# zane_bench_results.txt. After editing them, rebuild the HTML with
#   python3 runbench.py --from-file
# which reuses that results file instead of re-running.

[Test 1]
Zane's bump-arena alloc (~88us median) comes in ~38x faster than malloc
(~3.33ms) and ~6x faster than Pool (~511us). The raw Arena baseline (~33us) is
still about 2.6x quicker, which is the harness's own per-object bookkeeping
rather than anything the memory model requires: objects carry no per-instance
metadata now that hosted objects are never relocated.

[Test 2]
Only the free loop is timed. Zane's frees are no-ops, so it finishes in ~0.06us
— effectively unmeasurable — while malloc (~3.15ms) and Pool (~570us) pay real
per-object cost. This is the bulk-reclaim model at its most extreme: nothing is
returned per object, so free order cannot matter.

[Test 3]
With four interleaved sizes Zane (~1.06ms) stays ~7.5x ahead of malloc
(~7.95ms) and ~2.8x ahead of Pool (~3.00ms): the bump arena has no size
classes, so mixed sizes are just more frontier bumps. The raw Arena baseline
(~84us) leads by an order of magnitude on the harness's own per-object
bookkeeping.

[Test 4]
No allocation is timed here — this is pure layout cost. Contiguous inline
storage (~125us) is the floor; the chunked layouts stay closer to it than the
pointer arrays do (UList ~157us, CChunked ~166us, against ~231us sequential and
~284us shuffled). This is the test that pays for keeping fields inline: a
densely packed run of objects beats a run of references by ~1.8x sequentially
and ~2.3x once access order is scrambled.

[Test 5]
Growing an owned buffer in place (~156us) beats C's realloc vector (~449us) by
~2.9x and the never-copy chunked forms by more (CChunked ~770us, UList
~1.32ms). The in-place path wins because the buffer is the dynamic frontier
allocation, so growth is a frontier bump rather than an allocate-and-copy.

[Test 6]
A guest is a u32 segmented offset naming the object's storage directly, so a
deref resolves in one chunk-directory lookup and then the field — no
indirection cell, because a hosted object never moves. The paths do differ in
loads: the segmented path reads refs[i], then the chunk-directory entry, then
Entity.hp, where the direct path reads direct[i] then Entity.hp. That extra
load is below this environment's noise floor, and the honest evidence for that
is the ordering itself: this run has the segmented path *slower* (~185us cached,
~180us reloaded against a ~172us direct baseline), while an earlier run on the
same binary had it faster. The two are not separable here. Do not read either
ordering as a result; read the test as showing no measurable penalty.

[Test 7]
At steady-state churn the allocators sit close (Pool ~3.08ms, Zane ~3.12ms,
malloc ~3.57ms): once entity counts stabilize, per-frame update and simulation
work dominate and the raw allocation gaps from Tests 1-3 mostly wash out.

[Test 8]
Sequential Zane (~11.18ms) and Pool (~11.58ms) lead malloc (~12.67ms) narrowly,
for the same reason as T7 — the per-frame update dominates. The work-stealing
variant (~62.39ms) is ~5.6x *slower* than sequential, which is an artifact of
the environment rather than of the model: this container has few schedulable
cores, so pool coordination costs more than the parallel update saves.

[Test 9]
Refilling a checkerboard-fragmented heap is where bulk reclaim shows its widest
margin. Zane refills in ~30us because the arena never fragmented — the frontier
simply advances and the freed evens are irrelevant. malloc (~3.29ms) and Pool
(~1.28ms) refill from the slots freed in Phase B and carry that history:
roughly 111x and 43x slower.

[Test 10]
Every run builds the full 4000-node tree — the builder gives each non-terminal
node at least one child until the budget is spent, and each build asserts the
budget reached zero, so the medians are not mixing tree sizes. The three Zane
variants differ only in how many guests they hold across teardown: none, one on
the root, or one per node, all created before the clock starts and read back
after it stops. They land at 50.52us, 54.75us, and 50.45us — note that the
middle figure is the *single-guest* case, so the ordering is not monotonic in
guest count and the spread is run-to-run variance, not a guest cost.

Note what is and is not measured. The timed region is the post-order walk
alone, so this is evidence that teardown cost is *independent* of how many
guests are outstanding, not a measurement of what a guest costs to create or
store. It is independent because arena teardown does no per-node free work and
a guest is a plain u32 copied from the host, with no cell to mint and nothing
to unregister — so there is nothing for the walk to do differently. malloc's
per-node free with coalescing is ~183us (~3.6x slower) and Pool is ~81us.

[Test 11]
The mixed workload compresses the field (Pool ~2.76ms, Zane ~2.76ms, malloc
~3.13ms): updates, scans, and randomized maintenance dominate the time, so the
allocator strategy is only a small slice of the total — the expected outcome for
a realistic churn pattern.

[Test 12]
Four read-only shards summed sequentially (~114us) beat the concurrent run
(~235us) on this machine. As in T8, that inversion is the environment: the shard
work is small and the container's core budget is contended, so pool
coordination costs more than the parallelism returns. Both produce the
asserted-identical total, which is the correctness point of the test.
