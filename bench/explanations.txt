# Benchmark result explanations.
#
# Authored after inspecting a real run of zane_bench (see
# zane_bench_results.json, and zane_bench_results.txt rendered from it).
#
# PROVENANCE AND NOISE. The committed run is a fresh full-suite run of the
# settled/roaming harness, the first since the anchor pool, the per-host
# backpointer and forwarding were removed (spec PR #212). It was taken on a
# different and less powerful machine than the previous pin, which ran under
# WSL2 with no core pinning on a hybrid desktop CPU of 8 performance and 16
# efficiency cores. Rows whose code did not change came in 1.9-5.1x slower
# here than in that pin, which is the machine, not the code, so no absolute
# figure here should be compared with one from before. Every comparison below
# is between rows of this run. The two threaded rows, T8 and T12, are the
# noisiest on either machine.
#
# Every row carries all 20 per-run samples in zane_bench_results.json, so the
# spread is checkable rather than asserted. In this run the first pass is the
# slowest in only 10 of the 49 timed rows, but where it is, it can dominate:
# 13x the median on T1's Zane row and 25x on T3's arena row. The median is
# taken over all 20 samples, warm-up included, and barely moves when that pass
# is dropped: T1's Zane row is 86.2us over all twenty and 85.0us over the last
# nineteen. Treat each figure as one run's median, good to about one
# significant figure. The durable content is the ratios, the orderings, and
# effects large enough to survive that band; where two rows fall inside it the
# note says they tie rather than picking a winner.
#
# runbench.py reads this file alongside the results and renders each block as
# the "Reading the result" note for its test — a section below that test's
# chart. It interprets the numbers; the configuration lives in the panel above
# the chart, and checked invariants live in that panel's meta rows.
#
# Format: one block per test, opened by "[Test N]". Lines starting with '#'
# are comments; blank lines separate blocks.
#
# Keeping this in sync: these notes are pinned to the measurements in the
# committed zane_bench_results.json. After editing them, rebuild the page with
#   python3 runbench.py --from-file
# which re-renders from that file instead of measuring again.

[Test 1]
Zane's bump (~86us) runs ~58x faster than malloc (~5.03ms) and ~6.5x faster
than Pool (~559us), and since only Zane's release is free, its figure is
allocation alone where the other two carry their frees inside it. Neither
Zane nor the flat arena (~39us) writes to the memory it hands out now that a
host carries no backpointer, so the ~2.2x between them is not cache-line
fills: the only code that differs is Zane's chunk-boundary check and the
frontier it keeps in its region record. The first of Zane's twenty passes
took ~1.14ms, 13x its median; the harness touches every page of the region
before any test runs, so that pass is warm-up of something other than page
faults, and the median is the figure to read.

[Test 2]
Zane's row is not a fast release loop; it is no loop at all. zm_host_release
is an empty function, so the compiler deletes the 100k-iteration loop outright,
and the harness reports the row as eliminated rather than timing two
timestamps around nothing. malloc (~2.27ms) and Pool (~681us) spend ~23ns and
~6.8ns an object returning blocks to a structure that later allocations must
search. Having the structure at all is the cost.

[Test 3]
Mixed sizes cost Zane nothing structural: ~708us, ~7ns a block, against
malloc (~9.90ms, ~14x) and Pool (~4.59ms, ~6.5x). Arena (~115us) is again
the floor. The ordering is the one T1 shows at a single size and the one the
previous two pins showed here; the multiples are the part to distrust, Pool's
having moved from ~3.8x to ~6.5x between pins on unchanged code.

[Test 4]
Layout alone spans ~2.8x. Contiguous inline storage (~127us) is the floor,
the chunked forms sit close behind (UList ~151us, CChunked ~171us), the
scattered pointer array costs ~204us walked in order, and ~350us shuffled.
The shuffle is back: ~1.7x the in-order walk, where the previous pin had the
two tying and the one before that had ~1.5x. A finding that appears in two of
three runs is a tendency rather than a result. The gap between contiguous
storage and any scattered form is what all three agree on.

[Test 5]
Zane's list (~473us) again leads C's realloc vector (~616us) by ~1.3x, and
CChunked (~703us) follows; UList (~1.89ms) is clearly last. Two pins now put
the same ~1.3x lead in front, which is enough to say growth at the dynamic
frontier is not behind a realloc that extends its mapping, if not enough to
call it a win. Bounding a block to one chunk is what forces relocation, and
it stays cheap because only the two oversized spans copy at all.

[Test 6]
A guest now costs what a pointer costs. Resolving a segmented offset (~195us
with the chunk directory hoisted, ~168us re-fetched) ties dereferencing a raw
pointer (~191us); the fastest passes, ~157us direct against ~163-166us
offset, agree to within 6%, and the re-fetched row coming in ahead is noise.
Under anchors the same test cost ~1.24x direct, which was the anchor-cell
load a guest no longer makes. The shift and mask that turn an offset into an
address are absorbed by the pipeline.

[Test 7]
Once entity counts stabilize the allocator stops mattering much: Zane
(~4.28ms), Pool (~4.56ms) and malloc (~4.99ms) span ~17%, with Zane nominally
in front of Pool by ~7%. The previous pin had Zane and Pool tied, so read
that lead as inside the noise. The order-of-magnitude gaps of T1-T3 have gone
into per-frame update work.

[Test 8]
Maximum churn is the one workload where Zane comes last: Pool ~12.2ms,
malloc ~15.1ms, Zane ~17.0ms, ~1.4x Pool. The fixed region never reuses a
freed slot before the scope drains, so each frame's spawns land in memory
the update loop has not touched, where Pool hands back the slots that just
died and are still in cache; that is the likely cost, and it is the price of
T9's flat refill. Zane's own passes spread from ~14.0ms to ~24.6ms, the
widest of the three. The work-stealing row is ~145ms, ~8.5x plain Zane:
per-frame particle work is too small to amortize scheduling, as both
previous pins also found.

[Test 9]
A bump frontier cannot be fragmented, and the refill shows it: Zane takes
~49us for the 50k objects, ~1ns each, and holds between ~48us and ~54us
across all 20 passes. It is also the one row in the suite that got faster
than the previous pin in absolute terms, ~77us then, on a run where every
unchanged row got slower: refilling no longer zeroes a backpointer in each
host. malloc (~2.28ms) and Pool (~1.19ms) refill from freed slots at ~46x and
~24x, and both degrade across the run: Pool's passes climb from ~379us to a
~2.24ms worst and malloc's from ~1.49ms to ~3.01ms, each cycle handing the
free list back in a worse order than it found it.

[Test 10]
Teardown of the branching tree: Zane ~62us, Pool ~79us (~1.3x), malloc
~152us (~2.5x). This is the first pin on the corrected topology, roughly
1,070 branch points at depth ~20-26 rather than the 4,000-node chain the
earlier figures measured, and the cross-allocator ordering survived the
change. Guest density no longer has a row, because a guest leaves nothing in
its host for teardown to visit; what Zane's walk does per node is return the
node's child list to its exact-size stack.

[Test 11]
The mixed workload compresses the field to a tie: Zane ~3.89ms, malloc
~4.08ms, Pool ~4.12ms, ~6% end to end. Updates, scans and randomized
maintenance dominate, so the allocator is a small slice of the total, and the
ordering has moved between every pin.

[Test 12]
Concurrency loses. The scan splits into four equal shards and waits for all
of them, so a pass runs at the speed of its slowest shard: concurrent passes
run ~248us at best, ~398us median and ~647us at worst, against ~114us
sequential (~89us best). Best against best is ~2.8x, close to the ~2.9x of
the previous pin and the ~3.1x an earlier run measured with the process
pinned to four cores, which is the figure to read; the median adds core
placement on top. Distributing a ~100us scan costs several times more than
doing it outright, because per-shard work this small cannot amortize the
handoff.

[Test 13]
Not knowing a size until runtime costs nothing measurable: ~688us for the
runtime size class against ~755us for the static one over 60,000 pairs, the
runtime row nominally ahead, as it was in the previous pin. The effect is
inside the noise, so the reading is that a runtime size class is free. The
stacks cost far more — the frontier-only row runs ~257us, ~2.7x under both —
and what they buy is memory rather than time: frontier-only bumps through
17.9 MB of fresh chunks to hold a 1 MB live set where the stack runs recycle
inside ~1.8 MB. Pool (~473us) stays ahead, by ~1.5x this time, because its
link is a raw pointer where §3.1 makes this one a segmented offset.

[Test 14]
An escape costs what a deep copy costs. Relocating the roaming tree out of
its scope (~84us) and deep-copying the value tree from an existing place
(~81us) both walk all 8,191 nodes and allocate a block for each; the escape
additionally returns each old block to its stack, and the two tie. A move
that does not escape copies only the root's handles and is not timed.
Constructing a fresh value tree in place (~46us) is the floor both sit ~1.8x
above, which is the copy itself and why only an existing source or an escape
pays it. malloc's deep copy is ~342us, ~4.2x.
