# Stories: Operators

> **See also:** [`spec/operators.md`](../spec/operators.md) — the rules these chapters explain.

## A small vocabulary worth overloading

Operators posed two questions that are easy to conflate: whether programmers could change what familiar notation means for their own types, and whether they could invent new notation altogether. We wanted the first and rejected the second. Refusing overloading, as Go does, would keep the language surface exceptionally plain, but it would also make every user-defined numeric, geometric, or collection type a second-class citizen. A vector that cannot use the same addition notation as a scalar has lost much of what operators are for. Overloading the built-in set was therefore essential.

That did not imply an open-ended operator language. Custom tokens bring custom precedence, or at least the question of it, and make a reader learn a local dialect before an expression can be grouped. We instead kept one small, fixed vocabulary whose implementations may vary while its grammar does not. This is a deliberate middle ground: abstractions may participate in ordinary notation, but they may not extend the notation itself. The cost is that a domain whose natural operation has no place in the fixed set must use a named verb, even where a bespoke symbol would be concise.

Overloading also exposed a broader question. An overloaded name is easy to resolve at a call, where the operands and their types are present, but ambiguous when passed as a value to another overloaded verb. We initially met that as an obstacle specific to functions. Operators showed that it was really a lapse in orthogonality: they work cleanly because an operator token is call-only and can never be detached from its operands. We applied the same rule to every verb. A programmer who wants behavior as a value writes a lambda, which is an ordinary expression and can be stored or passed without asking an overloaded name to choose an implementation in a vacuum. That gives up the convenience of passing a bare function or operator name, but it gives all verbs one resolution model instead of adding special rules for each callable form.

## One operator for flipping a value

The unary vocabulary became constrained before we chose its spelling. `!` had already been reserved to make mutating method calls visible, so it could not also mean boolean negation. At the same time, a preference for orthogonality made separate unary `-` and boolean-NOT operations look wasteful. Additive inverse and logical complement perform the same higher-level act: they **flip** a value. That idea extends beyond numbers and booleans; vectors and other composite values can define what their own flip means without requiring another unary concept.

We still needed a symbol for it. Unary `-` was familiar for numbers, but reusing the subtraction token would obscure the fact that this was a universal operation and would produce the jarring `-true` for booleans. `!` was already occupied, and using it in the derived spelling of subtraction would make that operation look alien. `~` resembled `-` closely enough to suggest reversal while remaining visibly distinct, and Lua's established `~=` spelling made the resulting inequality notation feel less invented. So `~` became the sole unary operator: logical complement for booleans, additive inverse for numbers, and the general flip point for types that define one.

The price is immediate familiarity. Readers coming from most C-family languages will first read `~value` as bitwise complement, and `~true` is less conventional than `!true`. Zane spends that familiarity to keep the unary model small and to leave `!` with one unambiguous job.

## Deriving the laws instead of trusting them

Once flip was primitive, several other operators no longer needed independent definitions. Subtraction could be addition of a flipped value; inequality could be flipped equality; and three comparisons could be expressed through `<` and flip. Letting a type implement those spellings separately would add flexibility only by permitting it to lie—for example, to make `a > b` disagree with `b < a`. Where a derivation is trivial, we preferred to make law violations inexpressible. The smaller implementation surface is useful, but it is the consequence rather than the point. It also rewards a type for defining the broadly useful `~`: one implementation unlocks several derived forms.

Division is the deliberate boundary. Deriving `a / b` as `a * (1 / b)` assumes a multiplicative inverse exists, and floating-point arithmetic makes even the apparently equivalent reciprocal-multiply transformation observably different. Compilers place such transformations behind relaxed floating-point semantics for exactly that reason. `/` therefore remains primitive: a type can implement division directly without pretending it is multiplication in disguise.

Derivation has a cost of its own. A domain cannot provide an efficient specialized `>` or `-` whose behavior merely agrees with the law; the fixed expansion is the only spelling the language recognizes. We accept that lost optimization hook because an operator law that tools and readers can rely on is more valuable than an extra implementation point.

## Grouping is grammar all the way down

Allowing implementations to vary made it more important that grouping never does. Precedence belongs to the grammar, not to types or declarations, so changing an operand type cannot reshape the expression around it. `and` and `or` remain keywords because their short-circuit behavior is control flow: an ordinary overloaded verb would receive already evaluated operands and could not preserve it.

The same orthogonality settles comparison chains. Python gives `a < b < c` a special chained-comparison meaning. We did not adopt that exception, nor did we prohibit the form to protect programmers from C-like surprises. Comparisons group left like the other binary operators, so the expression means `(a < b) < c`. Usually that second `<` has no matching overload and the program is rejected; if a package deliberately defines `<` for the boolean result and the third operand's type, the expression is valid. The grammar does not decide that one sequence of operands deserves a special interpretation.

This rule permits code that many readers will initially assume is either forbidden or Python-like, and a deliberately unusual boolean comparison overload can make it meaningful. That is the honest cost of total regularity here. Parentheses remain the way to communicate an intended grouping when the conventional reading would be uncertain.

## Imports may add names, not meanings

The last pressure came from separate compilation and ordinary maintenance. If any imported helper package could contribute an operator overload, adding or removing an import could silently change the meaning of an existing `a + b`. We wanted edits to imports to affect the names a file may mention, not reinterpret expressions that were already valid.

Operator implementations therefore belong to the home package of at least one operand type. A unary operator lives with its operand; a binary operator lives with either side. Resolution can find the candidates from the types already present in the expression, without treating the import list as an invisible extension registry. This follows the same coherence instinct as home-package methods, but operators make the danger sharper because their names are punctuation and the declaring package never appears at the call site.

The restriction closes off retroactive adaptation in a neutral third package. When two foreign types ought to interoperate, their operators cannot be supplied by an unrelated bridge package; one of the home packages must own the integration, or the caller must use a named conversion or verb. We take that friction over allowing a seemingly harmless import to rewrite the meaning of existing notation.

## `and` and `or` become `*` and `+`

Once branching had left the language, one oddity was left standing where everything around it had a category. `and` and `or` were not operators — the fixed set is symbolic and they are words — and they were not functions either, because a function receives evaluated arguments and short-circuiting is precisely the refusal to evaluate one. They were keywords, which is a category with exactly two members and no principle behind it.

The first diagnosis we reached for was wrong and worth recording, because it sent us down a road. The complaint sounds like *these are tied to `Bool`, and the language should not be tied to a type* — the same complaint that moved `if` into `core`. It is not. `~` is tied to `Bool` too, and cleanly: it is an ordinary primitive operator with a `Bool` implementation, and nobody minds. What made `and` different was never the type; it was the unevaluated operand. Get deferral and the oddity is gone.

That reframing made the answer smaller than expected, because `a and b` *is* a conditional — run `b` when `a` holds, otherwise `false` — so it needed no mechanism the block work had not already built. And since the operator vocabulary is fixed, the honest question became which existing tokens carry the meaning. `*` and `+` do: a Boolean algebra is a semiring, conjunction is the product and disjunction the sum, and the language already names sums and products elsewhere for the same underlying reason. So `Bool` implements the primitive set like any other type ([`operators.md` §2.4](https://github.com/zane-lang/spec/blob/0aae01df1c8d3480805b5c4d8353f6f643a3f525/spec/operators.md#24-boolean-operators)), and the derived operators supply the rest for free — `~=` is inequality, which on two booleans is exclusive or, and `a - b` is `a + ~b`, which is implication.

Two things fell out that we did not choose and could not have chosen otherwise. `-` cannot be exclusive or, however much one might want it there, because subtraction is already a fixed desugaring and `a + ~b` is what it says; the meaning was assigned before the question was asked. And the logical reading cannot generalize past `Bool`. Conjunction and disjunction are interderivable through the complement, and `~` on `Int` is an additive inverse rather than a complement, so the identity simply fails there — `~(~2 * ~3)` is `4` where `2 + 3` is `5`. There is no coherent `3 and 4` waiting to be defined, and the tokens on `Int` stay arithmetic. Asking whether a type may have the logical reading turns out to be asking whether its `~` is a complement, and that is a real answer rather than a rule we imposed.

The short-circuiting went, and we let it go deliberately. Operands are evaluated, because these are ordinary operator calls and nothing about a token should silently change evaluation order. What replaces it is an overload taking a deferred right operand, which puts the choice at the call site where a reader can see it — the same move as marking a mutating call with `!` rather than leaving it to be inferred from a declaration elsewhere. The cost is that `cache:has(k) * expensive(k)` runs `expensive` unconditionally, and someone will be bitten by it; the compensation is that the version that does not is visibly different on the page.

## The loose operator forms and the `'` prefix

Reusing `*` and `+` put conjunction at the wrong precedence, and we did not see it until we tried to write a condition with it, because the break was silent.

`*` sits at precedence level three and comparisons sit at five, the loosest. So conjunction binds *tighter* than comparison — backwards for every compound condition anyone writes. `age > Int(18) * hasId` groups as `age > (Int(18) * hasId)`, which at least fails loudly on the missing `Int * Bool`. `a == b * c == d` with four booleans does not fail at all: it groups as `(a == (b * c)) == d`, type-checks, returns a `Bool`, and is not the conjunction of two equalities that was written. `and` and `or` never had this problem for a reason nobody had had to state: they sat below everything.

The escape we could not take was giving `*` one level for `Bool` and another for `Int`. Grouping in Zane is syntax and never depends on types — that rule predates all of this and is not worth spending here, since an expression whose shape you cannot read without knowing the operand types is worse than any spelling problem it would fix. That left parenthesising every compound condition, which works and is what the language already offers, but turns the common case into a pile of brackets.

So a binary operator gained a **loose form**: the same token with a leading `'`, calling the same implementation from a mirror of the table placed below every unprefixed level ([`operators.md` §3.1](https://github.com/zane-lang/spec/blob/0aae01df1c8d3480805b5c4d8353f6f643a3f525/spec/operators.md#31-a--prefix-selects-the-loose-form-of-a-binary-operator)). `age > Int(18) '* hasId` groups the way it reads. The mirror preserves relative order rather than flattening to a single level, so `'*` still binds tighter than `'+` and a chain of conditions nests the way conjunction and disjunction ought to.

Three bounds keep this from being the thing the fixed-precedence rule forbids. It is one tier deep — `''*` is not a further shift, because iterated shifting would be a program choosing its own precedence levels in all but name. It is binary only: unary `~` binds tightest and has nothing to separate itself from, and pipe syntax was never part of the operator set. And it introduces no token, since `'` selects an operator that already exists at a level that is already fixed. The vocabulary stays closed and grouping stays a property of the grammar.

The character was the last question, and `.` — the obvious choice — was the wrong one. It already carries field access, named constructors, and variant case forms, and the whole delimiter scheme rests on one character meaning one thing per context. `'` was free, and unusually cleanly: it had been the borrow marker for exactly one release of the design, and when that mode was removed it went back to being a character the lexis does not use. Taking it back was worth being deliberate about rather than defaulting into, but a mark that had already been reserved once, and is followed by punctuation rather than a name, costs nothing to reserve again.

## Written order survives the swap

Deriving the comparisons from `<` settled which operand each primitive receives, and left a question the table could not answer: when. Two of the five desugarings hand `<` its operands the other way round — `a > b` is `b < a`, and `a <= b` is `~(b < a)` — so a compiler that rewrote the text literally would evaluate the written right operand first. That would not matter if operators were arithmetic on plain values, but they are ordinary verbs, and only `~` is required to be pure. `f(log) > g(log)` can make two observable writes, and a literal reading of the table puts `g`'s first.

We could have left the order unspecified, which is what C does for most of its operators and what [`effects.md` §3.2](https://github.com/zane-lang/spec/blob/041f95eeae0e6f8ad79d515a5cb88eee040db87c/spec/effects.md#32-level-2--pure) already permits for a Pure verb, whose calls may be reordered because nothing can tell. For a verb with effects that freedom is a trap: the program means one thing on one compiler and another on the next, and nothing at the call site says which. We could instead have let the order follow the desugaring, which keeps the table a complete description of behaviour but makes `>` and `<=` evaluate right to left while `>=` does not. A reader would then need to remember which of the five swap — the very detail the derivation exists to keep out of sight.

So the operands of every operator are evaluated left to right, as written, and only then passed in the positions the desugaring gives them ([`operators.md` §2.3](https://github.com/zane-lang/spec/blob/041f95eeae0e6f8ad79d515a5cb88eee040db87c/spec/operators.md#23-derived-operators)). The table still decides what `>` means; it no longer decides when its operands run. That is the order a reader assumes before they have ever seen the table, and it matches the one the spec already fixes for map literal entries.

The cost lands on implementations. The desugaring is no longer a rewrite of the source text, because the text it produces would evaluate in the wrong order: a compiler has to keep the operands where they were written and apply the swap separately, by marking the call or by binding both operands to temporaries before the reordered call. Where both operands are Pure, the old freedom returns as a consequence — no program can observe the difference, so an implementation may still evaluate them in whichever order suits it.

## Primitives lose their operators to `@operators$` functions

Every operator so far had been declared by a package, on a type that package owns, and that left the storage primitives in an awkward spot. Something had to add two machine words, and the first answer was that the primitives themselves did: `@primitives$Int` came with a `+`, a `*`, a `<` of its own, found by the same home rule as any operator, with the namespace standing in for a package. That made the spec's claim that every intrinsic has exactly one signature quietly false, since an operator overloaded on its operands was a second exception beside methods that nobody had written down. And it did something worse than break a sentence: it made the primitives a numeric type a program could be written in. A file could alias `@primitives$Int`, compute with `+` and `<`, and never touch `core`. That is the opposite of what the primitives are for. They are the storage floor under `core`'s types, and nothing above `core` is meant to stand on them directly.

So we took their operators away entirely. The home rule already says how: a binary operator lives in the home package of one of its operand types, and a storage primitive's home is the intrinsic namespace that holds it, which is not a package ([`operators.md` §2.2](https://github.com/zane-lang/spec/blob/90275da88e310a53e67b5dea80bcb312bf15946a/spec/operators.md#22-where-operators-may-be-defined)). No package can declare an operator over primitives alone, so none exists, and a type that wants `+` declares it on a type of its own. What is left is the machine operation underneath, which has to live somewhere, and we gave it a namespace of its own, `@operators$`, named for what its members are for: they are what a package's operators are written over ([`operators.md` §2.6](https://github.com/zane-lang/spec/blob/90275da88e310a53e67b5dea80bcb312bf15946a/spec/operators.md#26-the-machine-operations-operators-are-written-over)).

They are functions, not operators, and that was the part worth arguing. The reason Zane uses operators at all is that the notation carries the mathematics: `a + b` reads as a sum, `a < b < c` can be chained in its loose form, and the left-operand-right shape is how people already write these things. All of that is the surface a type presents to the programs that use it. Inside `core`, where `Int +(left Int, right Int)` is written once and read rarely, there is no notation to preserve, and a named call says exactly which machine operation runs. It is the same move that put `if` over `@controlflow$branch`: the familiar form is a declaration, and the intrinsic beneath it is a plain call. The set follows the primitive operators of [`operators.md` §2.1](https://github.com/zane-lang/spec/blob/90275da88e310a53e67b5dea80bcb312bf15946a/spec/operators.md#21-primitive-operators) — `add`, `multiply`, `divide`, `equal`, `lessThan`, `negate` — and has no `subtract`, because subtraction is already defined as `a + ~b` ([`operators.md` §4.2](https://github.com/zane-lang/spec/blob/90275da88e310a53e67b5dea80bcb312bf15946a/spec/operators.md#42-subtraction-is-definitional)), and a machine operation for it would be an independent `-` beneath the derivation.

`Bool` was the first real fork. Its operators reuse the arithmetic tokens — `*` is conjunction and `+` disjunction, as [the earlier chapter](#and-and-or-become--and-) argued — so the obvious move was to reuse the arithmetic names too, with `add` overloaded on two `Bool`s as `or`. We turned that down. The case for `*` and `+` was that the notation fits the algebra and buys the infix form, and neither half survives the move to a named function. `@operators$add(ready, checked)` does not read as a semiring; it reads as arithmetic on booleans, and a newcomer meeting it would be right to be confused. So `Bool` has `and`, `or`, and `not`, and `String` has `concat`, each named for what it does. `equal` is the one name that spans all three kinds of primitive, because equality means the same thing on every type.

The second fork was about mixing. The first sketch overloaded every arithmetic operation on all four pairings of an integer and a float, so that `@operators$add` would take an `Int` and a `Float` in either order. That looked convenient until we asked what the machine does, which is not a mixed add at all: it converts one operand and then adds two of the same kind. A mixed overload would hide that conversion, and the conversion is a decision — an integer above 2⁵³ does not survive becoming a double — that belongs where a reader can see it, in `core`'s own source, not inside a compiler table. So every machine operation takes operands of one type, with one overload per type, and converting is a separate, written step; how that step is spelled is the subject of [the types story](types.md#the-scalar-primitives-become-i32-i64-f32-and-f64-converted-by-constructor).

The cost falls on anything below `core`. Until a `core` exists, a program that computes on primitives writes `@operators$add(a, b)` where it would have written `a + b`, and the derived operators are harder to reach than they look. A type whose `<` returns `@primitives$Bool` gets `>` for free, but not `<=`, because `<=` is `~(b < a)` and nothing can declare `~` on a primitive; the derivation needs a `Bool` whose package declares its complement, which is `core`'s. We accept that, because it is the design working as intended: the operators belong to the types programs are written in, and the primitives are not those types.
