# Stories: C Interface

> **See also:** [`spec/ffi.md`](../spec/ffi.md) — the rules these chapters explain.

## A C interface that keeps compile-time evaluation

The math functions had already turned a C interface down once. [The math story](math.md#math-as-intrinsics-not-a-c-foreign-function-interface) chose intrinsics for the square root and left a C interface for the libraries that really are written in C, with a list of questions it would have to answer first: how C code that can write a file with no capability fits an effect model with no ambient authority, where C pointers go in a language of owners and references, what C does to the guarantees a spawned call relies on, and how a program that links C stays something one machine builds for every target. Those libraries did not stop existing. Compression, hashing, image decoding, SQLite: a language without a way to reach them has to rewrite each one before its programs can use it.

One more question sat under that list, and it decided the shape of everything else. The math story had noted in passing that a call into C is opaque to the compiler, so a computation that passes through one can no longer be done at compile time. Every C interface we looked at accepts that. A Rust `extern` function, a Zig function from `@cImport`, a cgo call: the compiler sees a declaration, assumes the worst, and evaluates nothing that depends on the call. For those languages it costs little, because compile-time evaluation is something a programmer opts into by writing `const` or `comptime`. In Zane it is not opt-in. The compiler may evaluate any computation that depends on no parameter and no read of capability-backed state ([`effects.md` §5.3](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/effects.md#53-compile-time-evaluation)), and it does so across package boundaries. An opaque C call would put a wall in the middle of that: a Zane function that computes a checksum through zlib, called with a string literal, would be the one computation in the program that could not fold, and so would everything built on its result.

So we turned the default around. A call into C is a computation like any other unless its declaration says it reaches outside the program ([`ffi.md` §5.4](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#54-compile-time-evaluation-of-foreign-calls)). Impurity is what the binding opts into; purity is what it gets by saying nothing.

What decided it was which of the two marks would actually be written. A default stays right only if the people who must leave it have a reason to, and only one direction gives them one. A binding author whose C function reads the clock, under our default, has every reason: left unmarked, the call folds and the program shows the time it was built, a bug the author will meet the first time they look at the output. A binding author whose C function is pure, under the opposite default, has none: left unmarked, the call merely runs at run time, the program is correct, and nothing ever prompts them to add the mark. GCC's `__attribute__((const))` and D's `pure` are that opposite default, a promise of purity a programmer may make and everything else unknown, and they are rarely written for exactly this reason. Opt-in purity would have left nearly every binding opaque, so the wall in front of compile-time evaluation and implicit parallelism would have stood wherever an author never thought of the attribute. Opt-in impurity puts the mark where leaving it out is noticed, so the authors who need it are the ones pushed to write it.

The cost of this default is that it is the dangerous one. A conservative default fails safe: a pure function left unmarked merely runs at run time. Ours fails the other way. A C function that reads the clock or the environment, declared as if it read nothing, is evaluated while the compiler runs, and the value the build machine saw is built into the program. Nothing reports it. The program simply gives the same answer on every machine, forever. We decided that this had to be stated outright in the spec rather than left to be inferred from the folding rule, as a requirement with its consequences listed ([`ffi.md` §5.5](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#55-a-foreign-verb-that-touches-outside-state-must-say-so)): a binding author who forgets will not be warned by the compiler, so the warning has to be in the text they read.

The word for the declarations came quickly. A **foreign verb** is a function or method whose body is a C function: "foreign" is the established word for code in another language reached through an interface, the F in FFI, and "verb" is already the spec's word for a function or method. Writing `foreign "symbol"` where the body goes kept every other part of the declaration ordinary Zane, and the symbol had to be a string because C names are not Zane identifiers: `sqlite3_open` has an underscore in the middle, and `SDL_Init` begins with a capital, which Zane's casing rule reads as a type.

## Impurity is a capability, not a comment

With purity the default, the next question was how a binding says the opposite. The first idea was a doc comment on the C side. A header already documents its functions, so a line like `/// @zane reads` above a prototype would put the mark next to the code it describes, in the file the binding author is already editing, without touching Zane's grammar at all.

We moved away from it for three reasons, and the first was the failure mode itself. A comment the compiler reads has to be exact, and a mark spelled `@zane read` or placed one line too high is not a syntax error; it is a comment. Since the cost of a missing mark is a silently wrong program, the mark is the last place we wanted a typo to be invisible. The second reason was that a comment marks a function as impure without saying who may call it. Any verb anywhere could call a function marked as reading the clock, which is exactly the ambient authority the effect model forbids ([`effects.md` §6.1](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/effects.md#61-capabilities-must-be-passed-or-stored-explicitly)) and the first question the math story had asked. The third was that Zane already has a way to say a call touches outside state. A capability is an object whose methods reach external state, a call through it with `:` reads that state, and one with `!` writes it. Nothing about a C function needed a vocabulary of its own.

So a foreign verb that reaches outside the program is a method on a capability ([`ffi.md` §5.2](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#52-what-a-foreign-verb-touches-follows-from-its-signature)). Without `mut` it reads; with `mut` it writes. A foreign verb that is a plain function, or a method on an object of the program's own, reaches nothing. The mark the binding opts into is the capability in the signature, which the compiler checks like any other type, and every call to it shows the capability at the call site.

That needed a capability for C to be called through. The console and the runtime were the only capabilities the compiler supplied, and C code reaches far more than either: files, the network, the clock, the environment, devices. We considered stretching `@runtime$Runtime` to cover it, but the runtime is the Zane runtime's own configuration, its thread pool and its arguments, and making it also mean "everything C can touch" would have given one object two jobs. So we added a third, `@runtime$System`, with one instance, `@program$system`, reached by the root package and passed on like the other two ([`ffi.md` §5.1](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#51-the-system-capability)). We weighed `@runtime$Foreign`, which names where the code comes from rather than what it reaches, and `@runtime$World`, which is accurate and too grand. "The system" is what a C programmer already calls the thing on the other side of a system call, so it is the word they will look for. C never receives the system as an argument: it is the capability the call is made through, so declaring a C function through it leaves the function's C signature as the library already wrote it.

The system alone was too coarse for libraries whose objects are themselves outside state. A SQLite connection is opened once and then used by every query, and each query writes the connection and the database file together. Expressed through the system alone, the connection would be a read-only parameter that C nonetheless writes. So a C object that stands for outside state is a capability in its own right, declared with `#capability` ([`ffi.md` §4.1](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#41-handle-and-capability)), and its `mut` methods are writes in the effect model's sense. Making one is itself a `mut` method on the system or on another capability ([`ffi.md` §5.3](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#53-making-a-foreign-capability-is-a-write)). That rule closed a hole we found while writing the examples: a verb holding a read-only system could otherwise open a file and own the result outright, turning a read-only capability into a writable one, which is exactly what the read-only rule for derived references exists to prevent.

We also considered the road the effect model had already turned down for Zane code, two keywords such as `reads` and `writes` on a declaration. They would have been checkable, which the comment was not, but they would have been the purity keywords Zane does not have, and they would still have left the ambient-authority question open. The capability answered both.

The cost is what the capability cannot do. It cannot make a binding author declare it: a C function that reads the environment, written as a plain function, compiles and folds, and that is why the requirement is written out with its consequences rather than left implicit. It is also coarse. Every capability call is taken to touch one shared external state ([`ffi.md` §5.6](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#56-concurrency)), so two writes through two different files are serialized as though they might collide. Zane cannot see what C code behind two capabilities shares, so it cannot prove they do not, and we preferred an ordering it can keep to a parallelism it would have to guess at.

## Evaluating C as the target runs it

Defaulting C calls to computations promised that they fold, and a promise of folding is a promise that the compiler can run the C code. The folding rule also says what running it must not do: it may change nothing the program computes ([`effects.md` §5.3](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/effects.md#53-compile-time-evaluation)). That ruled out the first way we thought of doing it.

The obvious mechanism was to compile the C code for the machine the compiler runs on, load it, and call it. It is fast, and it is wrong whenever the build machine is not the target. C's own types change size between targets, `long` most famously, and a compression library computes differently with a 32-bit `long` than with a 64-bit one. A cross build for Windows from Linux would fold every call with Linux's answer. The approximate math functions had met the same trap ([the math story](math.md#exact-and-approximate-functions-in-one-namespace-math)), and they had settled it by leaving the platform library to run time.

So the compiler evaluates the C code as compiled for the target: the same code the program will run, read in its compiler's intermediate form with the target's layout of every type, and executed by an evaluator inside the compiler rather than by the build machine ([`ffi.md` §5.4](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#54-compile-time-evaluation-of-foreign-calls)). A call that reaches a function the build has no body for, such as a function of the platform's C library, stops the evaluation and is left to run time. That makes the approximate math functions behave in C exactly as they do in Zane: a C routine that calls `sin` does not fold, because `sin` is the platform's.

Two settings of the C compiler had to be fixed for this to hold. A C compiler may contract a multiply and an add into one fused operation, and whether it does can differ between the code it is asked to inspect and the code it finally emits, so the same expression could round once at compile time and twice at run time. A fast-math mode lets it reassociate floating-point arithmetic at will. Either would make a folded result differ from a run one, so both are fixed off for every package's C code, and no setting a package gives turns them back on ([`ffi.md` §2.2](https://github.com/zane-lang/spec/blob/f1432008d984ac170332dd1fa4f1cda2f872d10d/spec/ffi.md#22-the-toolchain-compiles-a-packages-c-code)). A library that was written to be compiled with fast math runs slower for it.

The cost is the evaluator itself. Running C's intermediate form inside the compiler is a substantial piece of machinery, much slower than native code, and it is bounded by the same budget as every other fold, so a large C computation stops folding long before it would have finished natively. It also needs the C code's bodies, compiled for the target, for every package whose calls it folds. That requirement settled the next question before we had finished asking it.

## The toolchain builds the C, and CMake does not

Who builds the C code was the question we had expected to argue about longest. A C library usually arrives with its own build: CMake, Meson, autotools, or a Makefile. The natural reading of "use a C library from Zane" is to let that build system remain in charge, build the library as it always has, and have the Zane compiler link the result. The alternative is for Zane's toolchain to compile the C itself.

Letting CMake manage the build would have meant one of two shapes. In the first, CMake drives everything and invokes the Zane compiler as one more compiler in the project. That fits a C project adopting some Zane, but not a Zane package: a library published with prebuilt objects for every target ([`dependencies.md` §3.1](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/dependencies.md#31-artifact-manifest-zane-artifactscoda)) would need CMake and a C cross compiler on every machine that builds from source, and a consumer of that package would need its build system before it could compile a line. In the second, the Zane toolchain runs each package's own build system, the way Cargo runs a crate's `build.rs`. That would have made fetching a dependency run whatever program the dependency ships, on the machine that fetched it, which sits badly beside a dependency model that verifies every byte it downloads. It would need the build system installed on the host, it would build for the host unless every build script got cross compilation right, and its output would depend on what else that host had installed.

Neither shape could have given the previous chapter what it needed. Folding a call into C requires the C code's bodies, compiled for the target, in the compiler's hands. Checking a foreign verb against its C declaration requires seeing the header with exactly the definitions and include paths the C code was compiled with, for each target ([`ffi.md` §3.7](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#37-the-declaration-is-checked-against-the-interface-header)). A library that comes out of someone else's build as an archive gives the compiler neither.

So the toolchain compiles a package's C itself, with the C compiler it already carries for every target, from settings stated as data. Zig took the same road with `zig cc`, and we put the C where Go's cgo puts it: the `.c` files in a package's directory are part of the package, exactly as the `.zn` files are. Nothing the package supplies runs at build time. Everything else followed from that. The C objects go into the release archive with the Zane objects, so a consumer needs nothing new. The C symbols are renamed into the package's namespace like its Zane symbols ([`ffi.md` §2.5](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#25-a-packages-c-symbols-belong-to-the-package)), so two versions of a package that vendors zlib coexist in one program, as two versions of anything else do.

Where those settings live took a second attempt. We first put them in a `c` block of the project's `zane.coda`, one row per setting with a column naming the package it was for. That was the wrong file. `zane.coda` and `zane-lock.coda` are written by commands, which keep the two in sync, and nobody edits them by hand ([`dependencies.md` §2.3](https://github.com/zane-lang/spec/blob/f1432008d984ac170332dd1fa4f1cda2f872d10d/spec/dependencies.md#23-files-are-recorded-and-updated-by-commands)), while a C build's source list, include paths and definitions are written by hand, as source is. So the settings moved into a `c.coda` in the package's own directory ([`ffi.md` §2.3](https://github.com/zane-lang/spec/blob/f1432008d984ac170332dd1fa4f1cda2f872d10d/spec/ffi.md#23-a-packages-ccoda)), and the package column went with the move. The file also travels with the package, so a package moved to another project keeps its C build without anything in the new project's manifest having to change.

The `.h` files directly in the package's directory became its **interface headers**: the headers that state the interface between the package's C and its Zane, as distinct from the library's own headers in its vendored tree, which only the C compiler reads. Keeping the declarations a foreign verb may name to a handful of files the binding author wrote gave the compiler a small surface to check, and gave the binding a place to adapt a C API whose types do not cross, which the next chapter needed.

The cost falls on the libraries with the most elaborate builds. A library that generates source at configure time, or that picks hundreds of files by probing the host, has to have its build written out again as a source list, as the projects that package C libraries for Zig's build system do. Some will not be worth it, so a package may also link a prebuilt archive or a library of the target system ([`ffi.md` §2.4](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#24-prebuilt-archives-and-system-libraries)). Those work, and they are what the C interface would have been everywhere had we chosen the other road: the compiler cannot read them, so nothing that calls them folds, and building for a target needs that library built for it.

## C never writes Zane memory

The last of the math story's questions was where C pointers would go. Zane has owners and references, settled and roaming, and a reference is minted only from a place that never moves. A C pointer is none of these, and it can point anywhere, outlive anything, and be written through by anyone who holds it.

Zig's answer is to let C's types into the language as they are, pointers included. That works for Zig because Zig has pointers already. Giving Zane a pointer type for C would have given every Zane program one, and every guarantee the memory model makes would have carried an exception for it. Passing addresses as integers was the same answer in disguise. We also looked at letting C write into Zane values passed to it, the out-parameters C APIs are full of. That would have made a parameter writable, and every parameter other than a `mut` method's subject is read-only ([`effects.md` §4.1](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/effects.md#41-a-read-only-binding-admits-no-write)), which is what the overlap rules and the spawn rules are built on.

So nothing Zane owns is ever written by C. Strings, arrays, and lists cross as read-only views that last for the call ([`ffi.md` §3.4](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#34-strings-arrays-and-lists-are-lent-for-the-call)), which is exactly what a borrow already is. What C needs to keep between calls lives in C memory, and Zane owns it through a **foreign handle**: a reference type that holds one C object and calls its release function when it is destroyed ([`ffi.md` §4.2](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#42-a-handle-is-made-by-a-foreign-verb-and-released-when-it-is-destroyed)). "Handle" is the word C APIs already use for the opaque pointer they hand out, so a binding author recognizes it at once. A handle that holds state of the program's own is a **data handle**, declared with `#handle`, and one that stands for outside state is the foreign capability of the earlier chapter. The `#` they carry is the one every reference type carries: a C object has identity, can be pointed at, and is moved rather than copied, so it sits on the reference side of the axis and gets settled and roaming owners, `&` references, and deterministic destruction for free. Only a `mut` method writes its subject, so C receives a writable pointer only there and a `const` one everywhere else, and the header check holds the C declaration to that.

The narrow set of types that cross was a choice of the same kind. A type crosses only if it means the same thing on every target, which is why `long` does not, and only if Zane can lend or copy it without C keeping hold of anything. The rest of a C API is reached through a small C function in the package that converts it, and that is cheap to write precisely because the toolchain compiles the package's C: a shim is one more `.c` file beside the binding.

The costs are concrete. A string returned from C is copied, once, into Zane's own storage. A C function that changes two objects at once has to be split into functions that each change one. A callback is a function value that does not capture, which is all Zane's lambdas are, so C APIs that pass a `void *` of user data back to their callback have no way to carry a Zane object through it. A C object that refers to another, a statement to its connection, is kept alive only if the binding says so with an `&` beside the handle ([`ffi.md` §4.4](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#44-a-c-object-that-depends-on-another)). And the boundary is a promise rather than a proof: C can still write through a `const` pointer or keep a view it was lent, and when it does the program has no meaning the spec defines ([`ffi.md` §6](https://github.com/zane-lang/spec/blob/b45aee26e4bca07cc732635e0c10f30f18f7d461/spec/ffi.md#6-what-foreign-code-upholds)). What the design buys is that the promise is small enough to state in a list, and that a binding that keeps it leaves every guarantee of the memory model standing on the Zane side.
