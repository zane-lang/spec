# Stories: Packages

> **See also:** [`spec/packages.md`](../spec/packages.md) — the rules these chapters explain.

## The directory is the package

Packages began with two jobs that were already the same boundary in practice: a namespace and a compilation unit. A directory holds the source that belongs together, and its basename is already the name by which that unit is known. We did not seriously consider a separate mechanism that lets a declaration choose some unrelated package. If `a.zn` sits in the `httpClient` directory, it belongs to `httpClient`; there is no second namespace assignment inside the file that can override where the file actually lives. All files in that directory compile as one order-independent unit, so a declaration in one file can use another without imports, forward declarations, or concern for file order ([`packages.md` §2](https://github.com/zane-lang/spec/blob/5ecd2b674577a514fea2f3be7270c0160d9d1af7/spec/packages.md#2-package-identity-and-compilation)).

> [!NOTE]
> Superseded: a package is no longer named by its directory's basename; the `name` field of its project's manifest names it. See "[The manifest names the package](#the-manifest-names-the-package)".

That made the written `package httpClient` line look redundant, but its redundancy is the point. Moving or copying a source file is a filesystem operation, often performed outside any language-aware tool. Without a declaration, the file silently changes packages when it changes directories, and several mistakes can follow from that one unnoticed move. Requiring every file to repeat the directory basename turns the line into an assertion: the directory determines membership, while the declaration records where the author expected the file to be. A mismatch makes the move visible immediately instead of allowing its consequences to surface later as unrelated name-resolution or visibility failures. The cost is one line repeated in every file. We accepted that small duplication because a safety check must carry independent information to catch the operation it checks.

> [!NOTE]
> Superseded: the declaration no longer repeats a directory basename; it repeats the manifest's `name`, and catches a file moved into the wrong project. See "[The manifest names the package](#the-manifest-names-the-package)".

The package boundary also became the visibility boundary. Names beginning with `_` are accessible across every file in their package and nowhere outside it; the same lexical marker covers types, aliases, constants, verbs, and every other named declaration, while symbol-named operators remain public ([`lexical.md` §4.2](https://github.com/zane-lang/spec/blob/5ecd2b674577a514fea2f3be7270c0160d9d1af7/spec/lexical.md#42-leading-underscore)). That choice belongs to [the lexical privacy story](lexical.md#privacy-lives-in-the-name), not a second packages rationale: the directory gives privacy its extent, while the name makes the boundary visible.

## A barrier that still joins the name

Once another package enters a file, we wanted every use of it to remain explicit. Importing `math` makes the namespace available in that file; it does not pour `math`'s members into the current namespace. A call stays `math$sqrt(value)`, in the spirit of Go's qualified package access. The extra package name is a small typing cost, and in return every cross-package reference tells the reader where it came from without consulting an import list or resolving collisions between identically named members. The current package is the only place whose members can be written unqualified ([`packages.md` §3](https://github.com/zane-lang/spec/blob/5ecd2b674577a514fea2f3be7270c0160d9d1af7/spec/packages.md#3-imports-and-member-access)).

> [!NOTE]
> Superseded: an imported member is no longer always qualified — the import form states its spelling, and may make it bare. See "[What an import writes is what the file writes](#what-an-import-writes-is-what-the-file-writes)".

Qualification still left a syntax question. A separator has to tell the parser, not merely the later name resolver, that its left side is a namespace and its right side is a member. A dot could not carry that fact. In `a.b.c`, the punctuation alone does not say which pieces are fields and which, if any, cross a package boundary. We considered `::`, the familiar namespace separator, but it was visually heavier than the operation deserved and sat too close to Zane's `object:method()` call syntax. A cross-package function such as `math::sqrt()` would make a package boundary look like a doubled method marker.

We chose `$` by looking for a single keyboard character that reads as a connection without disappearing or demanding attention. It forms a clear barrier between the two names, yet its width makes the expression look held together; a thin mark such as `¦` split the pieces without visually joining them. The result gives the parser the category boundary directly: `packageName$member` cannot be mistaken for a field chain or a method call ([`packages.md` §3.4](https://github.com/zane-lang/spec/blob/5ecd2b674577a514fea2f3be7270c0160d9d1af7/spec/packages.md#34--separates-a-package-namespace-from-its-member)). The cost is an unfamiliar separator where other languages reuse `.` or `::`; Zane spends that familiarity to preserve one meaning for each delimiter and to keep the namespace crossing visible.

## State has to be a value

A namespace and compilation unit can easily turn into a singleton object by accident. Permit mutable variables at package scope and any function in the package can read or change time-varying state without receiving it. For Zane that is not merely the usual objection to globals. It would destroy the effect model: a call whose visible inputs contain no mutable receiver or state-bearing parameter could still mutate hidden storage, so the signature would stop carrying the information effect inference relies on.

We therefore did not try to make package mutation safer with initialization-order rules, synchronization, or a special global effect. Those approaches preserve the hidden channel and then build machinery around it. The simpler answer is that mutable state is a value. Put it in a `struct` or reference-typed object and pass or store that value through the ordinary ownership, receiver, and capability mechanisms. Packages may still expose immutable constants and verbs, but no time-varying package slot exists ([`packages.md` §5](https://github.com/zane-lang/spec/blob/5ecd2b674577a514fea2f3be7270c0160d9d1af7/spec/packages.md#5-package-scope-state)).

This rule makes some programs more explicit than a global-state design would. A shared service, cache, or registry needs an object, and code that uses it must receive a path to that object instead of reaching through a package name. That wiring is not accidental ceremony; it is the evidence that lets the effect model see where mutation can happen. Packages organize declarations. Values carry state.

## What an import writes is what the file writes

[The barrier that joins the name](#a-barrier-that-still-joins-the-name) settled that an imported member stays qualified, and gave a good reason: every cross-package reference tells the reader where it came from, without an import list to consult or a collision to resolve. That reason has not weakened. What changed is that a second thing arrived which the rule could not accommodate.

`core` became an ordinary package ([its own story](dependencies.md#core-becomes-an-ordinary-package-over-a-primitive-floor) tells why), and `core` is the package whose members appear in every line of every file. Under one mandatory spelling, `core$Int` would have been written more often than any other token in the language. The rule was not wrong; it was calibrated for a package you reach for occasionally, and `core` broke that assumption by being universal.

The escape we did not take was to give `core` an exemption — predeclared names, or a blessed always-unqualified package. That is the carve-out the [previous account of cutting core loose](dependencies.md#cutting-core-loose-from-the-toolchain) had already identified as the expensive part, and re-adding it under a different name would have meant one rule for reaching `Int` and another for reaching everything else. If the qualification rule cannot hold for the package everyone uses, the honest conclusion is that it should not have been a single rule at all.

So the import *states* its own spelling, and there are several ([`packages.md` §3.3](https://github.com/zane-lang/spec/blob/0aae01df1c8d3480805b5c4d8353f6f643a3f525/spec/packages.md#33-the-import-form-fixes-how-its-members-are-written)). `import math` keeps `math$sqrt`. `import math$sqrt` makes it bare. `import math$sqrt as root` renames it, `import math as m` renames the qualifier, `import math$[sqrt, pow]` takes a few, and `import math$` takes everything. The organizing idea is that what appears after `import` is what appears at the use site — the qualifier ends wherever the import ends it — which is the same species of rule as choosing a delimiter by what it separates.

The property that keeps the original reason alive is narrower than qualification but does most of its work: **each imported entity has exactly one spelling in a file** ([§3.4](https://github.com/zane-lang/spec/blob/0aae01df1c8d3480805b5c4d8353f6f643a3f525/spec/packages.md#34-each-imported-entity-has-exactly-one-spelling)). An `as` rename does not add a name, it replaces one. `import math` and `import math$sqrt` cannot both appear, because `sqrt` would then be reachable two ways. A reader still cannot be looking at two names for one thing; what they lose is the guarantee that the name itself carries its origin, and they now recover the origin from an import list at the top of the file rather than from the call site. That is the real cost of the change and it is not small — it is exactly what the older chapter was protecting.

The rest fell out of rules already in place, which is usually the sign that a shape is right. Importing a single overload of a verb is not expressible, because an overloaded name is a set that only a call site collapses, so a member import takes the whole set or nothing. Colliding bare names are legal precisely when they form a valid overload set — verbs differing in parameter types — and are otherwise an error at the import declaration rather than at the use site, so the conflict is reported where the imports are listed. An `as` alias keeps the initial case of what it renames, because case is semantic. And an import reaches plain-name resolution only: it contributes no operator candidates, changes no method lookup, and alters no implicit-constructor visibility, each of which is settled by a home package rather than by what a file happened to import. Methods and operators are therefore not importable at all — not a restriction added for this feature, just the observation that neither was ever reached by a plain name.

It is worth being clear that none of this is a linkage mechanism. An import is a spelling and nothing else: every name resolves to its fully qualified declaration before anything downstream sees it, and the package name a compiled symbol carries is the defining package's own, whatever the importing file chose to call it.

## The manifest names the package

[The first chapter](#the-directory-is-the-package) named a package after its directory, and nothing contradicted that until we wrote down what a project looks like on disk. The dependency design had long since put a project's source in a `src/` directory beside its manifest ([`dependencies.md` §3](https://github.com/zane-lang/spec/blob/ff4909eb71a564174b416df08674af8bcaf4a906/spec/dependencies.md#3-repository-layout)), and the moment a tool had to create one, the two rules met: the directory holding every project's source is called `src`, so every package in the language was named `src`. Each file would open with `package src`, and every exported symbol would carry `src` where its name should be. [The hash in the symbol](dependencies.md#two-packages-called-math) would still have kept two libraries apart at link time, but the name after it is there for the person reading a symbol dump, and `src` tells that person nothing.

The basename rule had to go, and three things could take its place. The first was the project's own directory, the one that holds `src/` and the manifest. It needs no new field, and for a fresh checkout it usually gives the right answer. But a directory name is something a filesystem operation changes. Cloning a repository under another name, or renaming the checkout, would rename the package, and the declaration in every file would then fail. That is the move [the first chapter](#the-directory-is-the-package) built the declaration to catch, now firing on an operation that should not matter. The second was the last part of the repository URL, which follows from the package's identity. A project being written has no URL yet, though, and the name would still be borrowed from a host's naming rules rather than chosen. The third was a `name` field in `zane.coda`, written once when the project is created ([`packages.md` §2.1](https://github.com/zane-lang/spec/blob/ff4909eb71a564174b416df08674af8bcaf4a906/spec/packages.md#21-the-manifest-names-the-package)). We took the field. It is the only one of the three that the author states rather than inherits from somewhere else.

The declaration check survived unchanged in purpose. Every file still repeats the package name ([`packages.md` §2.2](https://github.com/zane-lang/spec/blob/ff4909eb71a564174b416df08674af8bcaf4a906/spec/packages.md#22-every-source-file-declares-its-package)), and a file copied in from another project still fails loudly, because what it repeats is now the manifest's name. Membership still comes from the directory: a package is the files directly in its project's `src/` directory.

That raised what a subdirectory of `src/` is, and we had not designed it. One plausible answer is that each subdirectory is a project of its own, versioned on its own and joined to its parent by [a local path dependency](dependencies.md#where-a-dependencys-code-comes-from). We did not commit to that. A `.zn` file in a subdirectory is a compile-time error for now, which keeps the space free for whatever the design turns out to be rather than giving it a meaning we would later have to take back.

The costs are small but real. A package's name can now disagree with every name a person sees on disk: a library whose manifest says `math` still compiles as `math` when it is cloned into a directory called `geometry-old`, and only the manifest says so. Renaming a package means editing the manifest and the first line of every file, which is the same number of edits as renaming the directory used to take, but the two places are now of different kinds. And a project gets one package until the subdirectory question is answered, so a larger codebase has to be split into separate projects to have more than one.

## A library's tests live in `test/` and import it as a consumer

A library could not be run. `zane run` refuses one, because there is nothing in a library for a user to start, and that left its author two ways to try the code they had just written, neither of them good. The first was to give the library a `main` of its own, which [the chapter on `kind`](dependencies.md#a-project-says-what-it-is) had kept legal for exactly this. But a library built on its own is the root of that build ([`packages.md` §6.1](https://github.com/zane-lang/spec/blob/a575f8371a69acc02bdc43f9eb26ac19fc9bc310/spec/packages.md#61-the-root-package-is-the-root-of-the-build)), and the root package reaches the program's console directly. The library was being exercised with a power that no consumer would ever hand it, so a library function that printed on its own worked under test and failed to compile in the first project that depended on it. The second way was an application project beside the library, joined to it by [a local path dependency](dependencies.md#where-a-dependencys-code-comes-from). That one tested the right thing, but it cost a second manifest, a second lock file and a second compiler pin for every library, all of which had to be kept in step with the first by hand.

What we wanted was the second arrangement without the second project, and Dart already had it. A Dart package keeps its tests in `test/`, and each test file imports the package the way any other program would. We took that shape: a library project may hold a `test/` directory, whose files form a second package that imports the library and is the root of the build that runs it ([`packages.md` §7](https://github.com/zane-lang/spec/blob/f1975dd28ab931f55669f0c01a65b0987dbd9a8a/spec/packages.md#7-the-test-package)). The point we cared most about is that the roles come out right with no rule written for them. The test package is the root, so it reaches the console; the library is a dependency, so it does not, and anything it prints has to arrive as a parameter, exactly as it will in a real consumer's build ([§7.2](https://github.com/zane-lang/spec/blob/f1975dd28ab931f55669f0c01a65b0987dbd9a8a/spec/packages.md#72-the-test-package-is-the-root-of-a-test-build)). The earlier sentence that a library *tested* on its own is the root of that build is the claim this retires.

The other well-known arrangement gives tests more reach rather than less. Kotlin's test source set is compiled into the same module as the code it tests and sees its `internal` members, and Go's test files sit in the package's own directory and see everything. Either would have let a test call a `_`-prefixed helper directly. We did not want it. [Privacy lives in the name](lexical.md#privacy-lives-in-the-name), and the rule is short because it has no exceptions; a test package that could see past it would make `_` mean "private, except to one other package", and every reader of the rule would have to learn the exception. Go's layout had a second problem of its own here: test files beside the source would sit in `src/`, which is precisely the set of files a release compiles. So the test package imports the library like anyone else, and reaches only what anyone else reaches ([§7.3](https://github.com/zane-lang/spec/blob/f1975dd28ab931f55669f0c01a65b0987dbd9a8a/spec/packages.md#73-the-test-package-imports-the-library-like-any-consumer)).

One part of Dart's design did not carry over. Each Dart test file has its own `main` and runs as a program of its own. A Zane directory is one compilation unit with no order among its files ([the first chapter](#the-directory-is-the-package)), so `test/` is one package with one `main`. We did not treat that as a loss. Discovering test functions, running each one and reporting which failed is a job for a library, and a testing library can be written in Zane like any other; the language gained a directory and a package name, and no test construct at all.

Rust suggested a split we weighed and declined. It keeps integration tests in `tests/` and runnable demonstrations in `examples/`, and we asked whether Zane wanted both a `test/` and an `example/`. The tooling could not tell them apart: each would be a root package importing the library and running a `main`, differing only in what that `main` does and whether CI runs it. Two directories would have meant two fixed names and two lists of extra dependencies for one mechanism. A demonstration that deserves to stand on its own can already be an application with a path dependency, which is what an example in another repository would be anyway. We also considered naming the one directory `consumer/`, which describes accurately what the package is to the library. It describes the mechanism, though, not the job, and it read badly everywhere it would appear: `zane consumer`, `package consumer`. `test` is understood without explanation.

The name is fixed, the way `src` is. We did not add a manifest field for it, since [the manifest names the package](#the-manifest-names-the-package) only because a published package's name reaches every symbol a reader sees in a dependency, and a test package is never published. Fixing it cost two reservations. No project may declare `name test` in its manifest, because its test package would then have to import a package with its own name, and no dependency key may be `test`, for the same reason.

A testing library is a dependency the library's consumers should never fetch, so the manifest needed a place for dependencies that only the test package uses. We put a `test-deps` block in the root `zane.coda`, beside `deps` and with the same columns, and a manifest fetched transitively has its `test-deps` ignored the way its `from` column already was ([`dependencies.md` §2.1](https://github.com/zane-lang/spec/blob/f1975dd28ab931f55669f0c01a65b0987dbd9a8a/spec/dependencies.md#21-manifest-zanecoda)). The alternative was a second `zane.coda` inside the `test/` directory. That would have made the test directory a project of its own, with its own name, compiler pin and lock file, and with pins for the library's own dependencies that could drift from the ones in `src/` — the second project we had set out to avoid, moved into a subdirectory. One manifest and one lock file keep a library's tests built against the same versions as the library.

The design is for libraries only, and that restriction is a real cost rather than a placeholder. An application's own package reaches the console, because it is the root of every build of the application. Make a test package the root instead, and the application's package becomes a dependency, which may not reach the console, so it stops compiling. An application therefore has no test package. Its author can still move the logic worth testing into a library of its own, at the price of a second project, which is the arrangement this chapter set out to spare libraries. The other costs are smaller. A private helper can be tested only through the public members that call it. And a library tested through a testing library that itself depends on the library under test, as a test of `core` would be, sees two copies of it in one program, which coexist like two versions and whose types do not mix; such a test has to keep the two apart.
