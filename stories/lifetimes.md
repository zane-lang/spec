# Stories: Lifetimes

> **See also:** [`spec/lifetimes.md`](../spec/lifetimes.md) — the rules these chapters explain.

## Inheriting a debt: safety without a borrow checker

This story begins where the [memory story](memory.md#safety-without-a-collector-and-without-lifetimes) ends. That story turned down two things at once — a tracing collector and a lifetime vocabulary — and built the anchor so that a ref stays valid even when its value moves. But the anchor only answers *where is the value now*; it says nothing about *how long may a ref live*. A ref that resolves correctly through its anchor is still a catastrophe if it outlives the owner it tracks: the owner drains, its storage is reclaimed, and the anchor now points at a corpse. Something has to guarantee the owner outlives every ref derived from it. In Rust that something is the borrow checker, and the memory story explicitly refused it. So the debt the memory story took on — "refusing the borrow checker means refusing the thing that makes the move problem go away by fiat" — comes due here, and not only for moves: the whole question of ref safety and ownership transfer has to be settled without a single line of lifetime inference.

The tempting road was to keep just a *little* inference — track where each ref flows, compute the region it must stay valid for, and check that against its owner. That is a borrow checker wearing a smaller hat, and it loses on the same ground the memory story already chose: it makes the compiler carry a proof the source does not state, and it forbids whole patterns with errors a beginner cannot read. We wanted the rule a programmer could run *in their head* while reading a single function — the language-wide preference for a readable rule over a more powerful one, the [foundations bet](foundations.md#strictness-is-the-performance-model) applied to lifetimes. So the resolution is almost aggressively simple: every lifetime question is decided by comparing **lexical declaration scopes**, and nothing else. An `&` may be assigned only when the target's owner is declared in the same or a higher scope than the ref ([`lifetimes.md` §1.1](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#11--assignment-uses-owner-scope)); a value may move into a new owner only when that owner sits in the same or a higher scope than the source ([§1.4](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#14-destination-scope-must-contain-or-match-source-scope)). A higher scope strictly outlives a nested one — that is what lexical nesting *means* — so "the owner is declared no deeper than the ref" is exactly "the owner outlives the ref," read straight off the source with no solver in between.

The cost is the honest one for any syntactic approximation of a semantic property: it is **conservative**. There are programs that are perfectly safe — a ref whose owner happens to outlive it through some control-flow path the scopes don't reflect — that the scope rule rejects anyway, because it judges by where things are *written*, not by what actually happens at runtime. We accepted that deliberately. The whole bet of the language is that a rule you can see beats a rule that sees more; a borrow checker accepts more programs and pays for it in a proof obligation and an error vocabulary, and that is precisely the trade the memory story already declined on the program's behalf.

## What may be moved: keeping ownership subtrees whole

With scope settled, the next pressure is the move itself: of all the things you could write on the right of a transfer, which ones are the language willing to *consume*? The unprincipled answer — anything that names a value — breaks the owner-uniqueness invariant the memory model rests on the moment you allow it to reach *into* an existing owner. So the rule narrows move-sources to two forms that share one property: each names a value **owned by no one else yet** ([`lifetimes.md` §1.2](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#12-move-sources-are-owning-symbols-or-owned-verb-results)). A direct owning symbol is owned only by its binding; a verb that returns an owned `T` hands back a fresh temporary owned by nobody at all. Moving either re-parents nothing, because there was no parent to disturb.

Everything else is a projection *into* an existing owner, and that is the road not taken. The obvious wish is to move a field out — `Truck(car.engine)` — or an element out of a container — `Garage(cars[1])`. Both are rejected, and the reason is that they would tear a hole in a live ownership subtree. If `car` still exists and you have spirited its engine away, `car` now owns a gap the type system swears is full; if a container yields up element 1, every index past it shifts or the slot goes hollow, and the container's own move-and-drop machinery — the very thing the [memory story's subscript rule](memory.md#where-a-new-ref-may-come-from) was built to protect — has no way to account for the theft. We could have tried to track the holes, marking fields and slots as moved-from and forbidding their later use, but that is exactly the per-element flow bookkeeping the memory model exists to avoid. So the language forbids the move at the source instead: a field or element is not a move-source, full stop. The containing object may be moved *as a whole* when it is itself a move-source, which keeps the natural-grained operation available and only forbids the fine-grained theft.

The cost lands on anyone who genuinely wanted one piece out of a structure: they cannot have it by moving. They must either move the whole container or design the piece to be independently owned from the start. That is a real expressiveness loss, and it is the price of the guarantee that any value reachable through an owner is *still there* — that ownership subtrees are stable, not gappy.

## The declaration-block rule, and the flow analysis it refuses

The scope rules say *where* a value may move to; this chapter is about *when* — and it is where the design pays the most to stay simple. A naive language lets you move a symbol from anywhere it is visible, including inside an `if`, inside a loop, inside a nested block. The instant you allow that, you have signed up for **flow-sensitive move tracking**: the compiler must reason that after `if cond { consume(x) }`, the symbol `x` is *maybe-moved* — moved on one path, live on the other — and must forbid every later use that cannot prove which path ran. That "maybe-moved" lattice is a substantial chunk of what a borrow checker *is*, and the errors it produces ("use of partially moved value") are among the hardest a newcomer meets.

Zane refuses the whole apparatus with one blunt rule: a direct owning symbol may be used as a move-source **only in the exact lexical block where it was declared** ([`lifetimes.md` §1.3](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#13-moves-are-restricted-to-the-declaration-block)). A symbol cannot be moved from inside a nested block, so it can never be moved on *some* paths but not others — the block that could move it is straight-line code, and a move there either always happens or never does. The maybe-moved state simply cannot arise, so the analysis that would track it is not needed. Parameters get the same treatment by fiat: they are treated as declared at the top of the function body block, which is exactly the place a callee is entitled to consume them.

The road not taken is Rust's, and it is worth being clear-eyed about what it buys: flow-sensitive tracking lets you write the conditional move directly, and the compiler proves it sound. We gave that up. The cost is that **a conditional move must be restructured** — you compute the destination or the guard *first*, then perform a single unconditional move in the declaration block, rather than scattering moves across branches. For a value moved inside a loop the restriction bites hardest, and the answer is the same: hoist the decision out, move once. This is more rigid than Rust, unapologetically. The compensation is that there is no flow-sensitive move error to decipher, because there is no flow-sensitive move analysis at all — the rigidity *is* the simplification.

## Downgrade, not poison: why there is no use-after-move-read

The previous chapter removes conditional moves; this one removes the error class that, in other languages, a move leaves behind even in straight-line code. After you move a symbol, what is the symbol? The defensive answer most ownership languages give is *poison*: the binding becomes unusable, and touching it — even just to read — is a compile error. That answer exists because in those languages a moved-from slot is genuinely dangerous; its contents have been logically relocated and reading them would be reading a ghost.

Zane already paid for a better answer, in the memory story. The [anchor](memory.md#the-move-problem-and-the-anchor-that-never-moves) was built so a ref keeps pointing at a value *through* a move; a moved-from symbol is just one more thing that wants to follow the value to its new home. So instead of poisoning the symbol, the language **downgrades** it: after the move the symbol becomes an `&` value resolving through the anchor, still readable, pointing at wherever the value now lives ([`lifetimes.md` §1.6](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#16-moved-symbols-downgrade-to--values-and-are-no-longer-movable)). What it loses is only the ability to move *again* — it is now an `&`, and an `&` is not a move-source — which is precisely the double-move the poison rule was protecting against, achieved without forbidding the read. The consequence is stated flatly in the spec and it is a genuinely unusual property: **Zane has no user-visible use-after-move error class for reads.** The same holds across calls; a callee that consumes a caller's value leaves the caller a readable downgraded `&`, so callee-decides move semantics ([§1.5](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#15-callee-decides-move-semantics)) never strands the caller with a poisoned name.

What is striking about this resolution is how little it costs. The downgrade rides entirely on the anchor machinery the memory model had already built and paid for, so it adds no new runtime mechanism; it removes an error class rather than trading one burden for another. The only thing it asks of a reader is to remember that a move quietly demotes the symbol — `engine` is an owner before the move and an `&` after, so the same name denotes slightly different storage on either side of the move point — and that is a small thing to carry next to the use-after-move errors it retires. This is one of the places where the honest account is that the decision was close to free, because an earlier chapter's machinery had already covered its cost.

## Returning a ref without a lifetime to name it

The last hole is the one lifetime annotations were *invented* for. A function returns `&T`; the scope rules of the first chapter govern assignments *within* a scope, but a return value crosses out of the function entirely, into a caller scope the function cannot see. What stops `&Int bad()` from returning a ref to its own local `value`, which dies the instant the function returns? In Rust the answer is a lifetime parameter `'a` that ties the result's validity to an input's — exactly the `'a` vocabulary the memory story refused to make the source speak.

The replacement is, once more, a rule you can check by looking: a function may return an `&T` **only when that reference is rooted in one of the function's parameters**, with `this` counting as a parameter ([`lifetimes.md` §1.7](https://github.com/zane-lang/spec/blob/9abc6748ebcbf3b27a011f7729b78f98f110d9f8/spec/lifetimes.md#17-returned--values-must-be-rooted-in-a-parameter)). The reasoning is that a parameter's owner necessarily lives in the *caller's* scope — the caller had to hold a real place to pass it — so a ref rooted in a parameter is automatically rooted in something that outlives the call. A ref rooted in a local is rooted in something that dies with the call, so it is rejected. No annotation is needed because the rule does not try to express *which* caller scope the result is valid in; it only insists the result trace back to one the caller already owns, and that is enough to be safe.

This is coarser than `'a`, and that is the cost. Lifetime parameters can express relationships this rule cannot — a result valid for the shorter of two inputs, a struct that borrows for a named region — and Zane simply cannot say those things. The expressiveness lands, as the memory story warned, on the **library author**: a function that needs to hand back a reference must arrange for it to flow from a parameter, and a design that wanted to mint and return a fresh interior reference has to be rethought. What the caller gets in return is the same bargain the whole document makes — a returned `&`, once the function compiles, is known to rest on ground the caller already holds, and no one had to learn a borrow vocabulary to get there.

## Consumed or borrowed: the parameter that lives at the call site

The [downgrade chapter](#downgrade-not-poison-why-there-is-no-use-after-move-read) closed on a claim it had not fully earned. It said a callee that consumes a caller's value leaves the caller a readable `&`, never a poisoned name — but it never pinned down *when* a passed reference is actually consumed, and the spec, read closely, gave two answers that could not both be true. One section described passing by the callee's behavior: store the value and it moves, leave it alone and ownership stays with the caller. Another described a plain reference parameter as *swallowed* — frame-local to the callee, gone when the call returned. The first says the value survives in the caller's hands; the second says it dies in the callee's frame. A reader trying to answer the plainest possible question — `engine Engine(); car Car(engine)`, where the constructor takes `engine` and does nothing with it, now what? — found the document contradicting itself.

The contradiction was not cosmetic, because the downgrade rule had already spent the caller's safety on one of the two answers. If a swallowed value is frame-local and dies with the call, then the caller's downgraded `&` — the thing the previous chapter promised stays readable — points at a corpse the instant the callee drops it. The very mechanism that made "no use-after-move-read" true depended on the passed value outliving the call, and one of our two accounts quietly denied it. We had shipped a latent dangling ref and hidden it inside a wording disagreement.

The tempting repair was to keep the "swallowed, frame-local" reading and simply forbid the drop: make a callee that takes a reference *have* to re-home it, and error otherwise. That works, but we chased it and it kept forcing the value *out* of the caller. Re-home into the return, and the caller must now write `x = f(x)` to catch its own value coming back — a manual reassignment at every call, the ceremony we least wanted. Downgrade the caller no matter what, and we were back to spending the caller's ownership on every call that only wanted to *look* at the thing. Each variant treated the callee's frame as the value's home and then negotiated the value's escape. The negotiations were the smell.

The move that dissolved all of it was to deny the premise: a parameter is **not part of the callee's body scope at all**. It belongs to the [call-site scope](https://github.com/zane-lang/spec/blob/faa3ceb822c5950e2499f035bd4384b77e5a0806/spec/lifetimes.md#15-parameters-belong-to-the-call-site), one level up, and the callee is merely handed owning access to it for the duration of the call. Once the parameter lives above the body, the body draining says nothing about the value's fate — a local that received it falling out of scope does not drop it, because the value was never the local's to drop; the compiler moves it back up to where it came from. The plain question answers itself: the constructor that does nothing with `engine` hands it back, and `engine` in the caller was never in danger, because it never left the caller's scope.

With the parameter rehoused, "consume" stopped being a behavior we had to observe and became a boundary we could name. A verb consumes a parameter exactly when the value escapes into somewhere the caller still tracks: into [another parameter's owning storage, or into the return value](https://github.com/zane-lang/spec/blob/faa3ceb822c5950e2499f035bd4384b77e5a0806/spec/lifetimes.md#18-parameter-consumption-is-inferred). Those are the only two exits from a call that land the value somewhere the caller can name afterward — an argument it still holds, or a result it catches. Everything else the callee does with the value — reading it, threading it through locals, lending it to nested calls — leaves it inside the call-site scope, so the caller keeps it whole. This is the general shape, and it reaches past parameters: a scope may take an owner from a higher scope, provided the value goes back to that scope, and the two ways back are the two exits a call actually has.

We had briefly wanted to keep returns *out* of the exits, precisely to kill the `x = f(x)` reassignment. We let them back in, because forbidding them made constructors impossible to state — a constructor's whole job is to consume its arguments into the object it returns — and because the reassignment worry has a cleaner answer than a prohibition: a [non-`Void` return simply cannot be ignored](https://github.com/zane-lang/spec/blob/faa3ceb822c5950e2499f035bd4384b77e5a0806/spec/lifetimes.md#19-a-non-void-return-value-cannot-be-ignored). If the value can ride out on the return, then dropping the return on the floor would drop the value, so we require every returned value to be bound or consumed. The constructor case then needs no special pleading: `car Car(engine)` consumes `engine` into the returned object, the caller binds `car` because it must, and `engine` downgrades to an `&` that now resolves into the car — every rule already in place, nothing added for constructors.

The last question was how a *caller* knows which happened, since `island!startMatch(player)` and `boat!loadCar(car)` look identical and yet one hands `player` back while the other swallows `car` into the boat. We refused to answer it with a new annotation. Zane already infers effect levels rather than making the source spell them, and consumption is the same kind of fact, so we made it inferred too: the compiler computes, per parameter, whether a verb consumes or borrows it, starting from the verbs that store or return directly and propagating outward to their callers. What keeps this from becoming the flow-sensitive tracking we spent [an earlier chapter](#the-declaration-block-rule-and-the-flow-analysis-it-refuses) refusing is the declaration-block rule: a parameter can only be moved in straight-line code, so it goes into a local or out through an exit as two separate static cases, never consumed on one branch and borrowed on another. The classification is a single bit per parameter, and it decides the caller's state — borrowed leaves a full owner, consumed downgrades to an `&` or is caught as the return — which is the refinement the downgrade chapter was missing: it is not that every call downgrades the caller, but that only a *consuming* one does.

The costs are real and we name them. The inference is interprocedural, so a verb's parameter modes are no longer a local fact — they depend on the verbs it calls, and a change deep in a call chain can flip a caller's parameter from borrowed to consumed. We accept the whole-program coupling because the alternative was an annotation on every reference parameter, and the language's standing bet is to infer what it can rather than make the source carry it. A sharper-edged cost is that a program's well-formedness now depends on the build: a plain `T` parameter a verb only reads should be an `&T`, and we make that an error *only in release builds*, letting development builds run with the looser form so a half-written function still compiles. Two builds can therefore disagree on whether the same source is legal — a genuine wart, chosen deliberately because the strict form is the one that reaches users and the loose form is the one that helps while the code is still moving. And there is one thing this design refuses to let you express at all: you cannot take a reference and destroy it *early*, before the caller's scope ends, because a passed value always outlives the call. Destruction stays tethered to the owning scope draining, exactly as the lifetime rules demand; a function that wants a value gone cannot grant that wish, and that is the price of a parameter that always belongs to someone above.

## The signature is the whole contract: retiring inferred consumption

The previous chapter closed on a design we were briefly proud of: consumption as an inferred fact, computed per parameter the way effect levels are, so the source never had to spell out whether a passed value came back. Reading it again with colder eyes, we found that the thing we had actually built was a rule you could not run in your head — the one property the [first chapter](#inheriting-a-debt-safety-without-a-borrow-checker) swore every lifetime rule in this document would keep. Standing at a call site, looking at `something(car)`, a reader had no way to answer the plainest question there is: *is `car` still mine after this line?* The answer lived somewhere else entirely — inside `something`'s body, and inside the bodies of everything `something` called, since the classification was interprocedural. The signature, the one thing right there on the page, said nothing. Whether `car` survived as an owner or quietly became a tether was a fact you had to go read another function to learn, and it could flip out from under you when that other function changed. We had traded an annotation we didn't want to write for a magic we couldn't see, and on this codebase that is a bad trade every time.

The tempting patch was to keep the inference and merely surface it — show the computed consumed-or-borrowed bit in tooling, let a reader hover a call and be told. But that concedes the whole game. If you need a tool to tell you what a line of your own code does to your own value, the language has already failed the read-it-in-your-head test, and dressing the failure in a hover tip does not undo it. The other patch was to keep inference for the common case and add an annotation for when you wanted certainty, which is the worst of the three: a rule that is sometimes inferred and sometimes written, so a reader must first work out *which mode is in force* before working out anything else. Every repair kept the callee's body in charge of the caller's fate and then tried to make the body's verdict easier to fetch. The verdict itself was the problem.

So we cut it. Passing an owning value to a plain `T` parameter [downgrades the caller's symbol to a tether](https://github.com/zane-lang/spec/blob/b932c539f2cb9c313fa1efabcd482481ec3b107a/spec/lifetimes.md#18-passing-an-owner-to-a-t-parameter-downgrades-it-to-a-tether), full stop, and the callee's body gets no vote. `T` in the signature means *the caller gives this up*; `&T` means *the caller lends it and stays the owner*. That is the entire contract, and it is legible from the call site because it is legible from the *signature* — the only thing a caller was ever reading. A verb that just glances at its argument and a verb that squirrels it into a field now look identical to the caller, and that is exactly right: both asked for `T`, both took an owner, and reading the value instead of storing it does not un-ask the question the signature posed. As the decision was put to us: nothing in the body changes what the signature already said. If a verb only wants to look, it must say so in the one place that speaks to the caller — by taking `&T`.

The mechanism this rests on was already built and already paid for. A [passed value still belongs to the call-site scope](https://github.com/zane-lang/spec/blob/b932c539f2cb9c313fa1efabcd482481ec3b107a/spec/lifetimes.md#15-parameters-belong-to-the-call-site), so it outlives the call whatever the body does with it; and the [downgrade-not-poison](#downgrade-not-poison-why-there-is-no-use-after-move-read) rule already turned a moved-from symbol into a readable tether through the anchor rather than a poisoned name. Passing to a `T` parameter is now simply a move like any other — the argument is a move-source, the symbol downgrades, the anchor keeps it resolving to wherever the value comes to rest. The elaborate part of the old design had been the *exception*: the borrowed case, where we chose *not* to downgrade because the body happened not to store the value. Deleting the exception removed no machinery; it removed a special case, and left passing-an-owner as an ordinary instance of the move rule this document already had. The old wart went with it — the *passing mode* no longer depends on the build, because there is no read-only-`T`-should-be-`&T` judgment left to relax in development and enforce in release. A read-only `T` is simply legal, and simply downgrades the caller, like every other `T`. Doing *nothing* with a parameter is still a release-build error, but that is the general unused-parameter rule, owner or not, and never had anything to do with consumption.

Getting an owner back, when you genuinely need it, is an explicit act rather than an inferred gift: the verb returns the owner and the caller binds it. That gives clean names to the two ways a verb can swallow an owner you hand it, told apart by its return — it **relays** it (`T`, and returns an owner you can rebind) or **consumes** it (`T`, returns nothing, keeps the value) — beside the `&T` tether, which swallows nothing and leaves you the owner outright. `car2 Car = repair(car)` says in plain sight that `repair` relayed the car and handed it back; there is no inferred alternative hiding behind it in which the same line would have left `car` an untouched owner. The reassignment is not noise obscuring a simpler truth — it *is* the truth, written where you can see it.

We first drew that last line too hard. To stop a dropped return from stranding the caller's tether, we made binding *mandatory* — a non-`Void` return could not be ignored. But the danger dissolves the moment you notice the value need not die when it goes unbound: it can [float to the enclosing scope](https://github.com/zane-lang/spec/blob/b932c539f2cb9c313fa1efabcd482481ec3b107a/spec/lifetimes.md#19-an-ignored-owned-result-floats-to-the-enclosing-scope), an anonymous owner living exactly as long as any scope-owned value, the caller's tether resolving into it. Nothing dangles, nothing is silently destroyed. And floating turned out *more* uniform than the mandate it replaced: passing an owner already leaves you a tether to a value that floats at the call-site scope, and ignoring a returned owner now does the identical thing — one rule, not a rule plus an exception. So binding stopped being an obligation and became a choice: take owning privilege, or don't. The choice even reads at the call site, since a caught return is exactly the mark that the caller wanted ownership back.

The cost is real and we name it. Handing an owner to a verb that only reads it is still perfectly legal — it just downgrades you to a tether, like any `T` pass. What is gone is the convenience of keeping *owner privilege* afterward for free; to keep it now you pass `&T`, deciding at the parameter's declaration that reading was all you meant. The loss is a genuine one in terseness, paid at every call that wants to lend-and-keep: what the inference used to hand back for free now costs either an `&T` at the parameter's declaration or a bound return at the call site. We took it deliberately, because the terseness it bought was precisely the terseness that hid the answer to *is this still mine*, and the standing bet of this whole document is that a rule you can see beats a rule that saves a keystroke. We also gave up the small elegance of parameter modes being inferable rather than declared: `&` on a read-only parameter is load-bearing now where it used to be optional, and a signature that gets it wrong is wrong at the call site rather than merely suboptimal. That, too, is a fair price for a contract that says what it means in the one place everyone reads.

## No rule to spare: the specific hole each restriction plugs

The chapters to here have each defended a *choice*: lexical scope over a borrow checker, downgrade over poison, the signature over inferred consumption. Set end to end they argue well for the *shape* of the system and hardly at all for its individual rules, and on re-reading that gap worried us. A reader could finish convinced that Zane simply favours blunt lexical rules as a matter of taste, and draw the reasonable-sounding conclusion that any one of them could be loosened a little, for convenience, at no real cost. That conclusion is wrong, and wrong in a specific way: each restriction is the minimal guard on one particular way a host and the value it hosts can be prised apart, and every one we imagined relaxing let back in exactly one concrete corruption. We had described the rules; we had never lined them up beside the disasters they exist to prevent. This chapter does that, once, because the honest case for the strictness is not the elegance of the system but the ugliness of what each rule is holding back. (The terms shift here from the earlier chapters' *owner* and *tether* to **host** and **guest**; the [memory story](memory.md#two-vocabularies-host-and-guest-above-anchor-and-tether) records why the names changed. The rules are the same rules.)

Start with the guest-assignment rule ([`lifetimes.md` §1.1](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#11--assignment-uses-host-scope)). It forbids binding an `&` to a host that lives in a *lower* scope than the guest, and only that direction — binding to a host in the same or a strictly higher scope is always fine, because a scope that encloses the guest outlives it by construction. The rule looks like fussy bookkeeping until you write the program it rejects:

```zane
outer Node()
r &Node = outer
{
    inner Node()
    r = inner
}
r:inspect()          // inner drained at the closing brace; r resolves to reclaimed storage
```

Nothing here is exotic — a guest reassigned inside a block, the sort of line anyone writes without thinking. And the runtime does its half perfectly: the anchor keeps `r` resolving to wherever `inner`'s value went, which after the brace is storage the scope has already reclaimed. The rule is the one thing standing between "the anchor tracks the value faithfully" and "the anchor tracks the value straight into its grave."

What keeps the rule from being mere caution is that it waves the mirror image straight through. Bind a guest to a host that *encloses* it and there is nothing to check — the host cannot drain before the guest does:

```zane
outer Node()
{
    r &Node = outer   // legal: outer encloses the block, so it outlives r
    r:inspect()
}
```

Here `r` is the short-lived one; it is gone at the brace while `outer` lives on, never for a moment tracking a value younger than itself. The restriction bites on exactly one direction because only one direction is dangerous — loosen it to admit the nested host and you have not bought a small convenience but reopened use-after-free in ordinary syntax.

The returned-reference rule ([§1.7](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#17-returned--values-must-be-rooted-in-a-parameter)) is the same hole seen from across a call boundary, which is why it needs its own guard rather than folding into §1.1: a return leaves the function's scopes entirely, into a caller the function cannot see. Let a function return an `&` to anything at all and this compiles:

```zane
&Node bad() {
    value Node()
    return value   // value dies as the frame unwinds; the caller is handed an & into reclaimed storage
}
```

`value` is gone the instant `bad` returns; the caller receives a live-looking guest onto a dead slot. Rooting the returned `&` in a parameter is exactly the condition that rules this out — a parameter's host necessarily lives in the caller's scope, so a reference that traces back to one is guaranteed to rest on ground the caller still holds. And "rooted in a parameter" is read transitively: the returned `&` may pass through an intermediate `&` binding, so long as that binding itself roots in a parameter. The coarseness is the whole point — the rule never tries to name *which* caller scope the result is valid for, only that it traces to one the caller already owns, which is all safety requires and needs no annotation to state.

The destination-scope rule ([§1.4](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#14-destination-scope-must-contain-or-match-source-scope)) closes the mirror image of §1.1. There the danger was a guest reaching down to a short-lived host; here it is a *value* moved down into one:

```zane
node Node()
{
    sink Node()
    sink = node       // node's value is now hosted by sink
}
node:inspect()        // sink drained at the brace, taking the value with it
```

The move re-parents `node`'s value into `sink`, whose scope closes at the brace and destroys everything it hosts. But `node` did not vanish when it was moved — it downgraded to a guest ([§1.6](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#16-moved-symbols-downgrade-to--values-and-are-no-longer-movable)) that stays readable, and after the brace that guest resolves, through the anchor, to a value the inner scope already destroyed.

The rule waves the opposite move through, and the symmetry with §1.1 is exact — swap which host is nested and the same assignment is safe:

```zane
sink Node()
{
    inner Node()
    sink = inner      // legal: sink encloses the block, so it outlives inner's value
}
sink:inspect()        // sink now hosts the value; nothing was stranded
```

A value born in the inner block and moved *up* into `sink` lands in a host that outlives the scope it came from, so no guest is left tracking something short-lived. The rule bites only on the lifetime-sinking direction, the only one that can strand a guest. It is close kin to the declaration-block rule, and for the same reason: both are about a move crossing a scope boundary it has no business crossing.

That declaration-block rule ([§1.3](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#13-moves-are-restricted-to-the-declaration-block)) guards a subtler failure — not where a value goes, but *whether it went at all.* Allow a symbol to be moved from inside a nested or conditional block and you get this:

```zane
car Car()
if damaged {
    scrapyard!crush(car)   // consumes car — but only on one path
}
car:inspect()              // on the crushed path, a read of a value already consumed
```

Now `car`'s state at the last line depends on a runtime condition: hosted on one path, downgraded on the other. A compiler that wanted to allow the conditional move would have to track that split — the *maybe-moved* state that flow-sensitive move analysis exists to compute, and whose errors ("use of partially moved value") are among the least legible any ownership language produces. The loop case is sharper still: a move inside a loop body consumes on the first iteration, and the second iteration moves an already-downgraded guest — a double consume with no single line to blame. Confining moves to the declaration block makes the move straight-line code, where it either always runs or never does, so the maybe-moved state cannot arise and the analysis that would chase it is never needed. The rigidity *is* the simplification: you restructure the conditional move — decide first, move once — and in exchange the whole category of partial-move errors does not exist.

The last of the five is the one whose loosening looks most innocent and costs the most to allow: the move-source restriction ([§1.2](https://github.com/zane-lang/spec/blob/54ac140005b0f4f330b24e86e0351bfd74b8fa25/spec/lifetimes.md#12-move-sources-are-host-symbols-or-hosting-verb-results)), which refuses to let a field or a container element be moved out. `Truck(car.engine)` reads like the most natural thing in the world — take the engine, give it to the truck — and that is precisely the theft the rule forbids:

```zane
engine Engine()
car Car(engine)
truck Truck(car.engine)   // imagine it allowed: engine spirited out of car
// car and truck now both host the one engine — and both destroy it when their scopes drain
```

Move the engine out and `car` is left hosting a gap the type system still swears is full; the single engine has two hosts, and deterministic destruction — the thing the whole document is built to deliver — dutifully destroys it twice. A container element is worse, because pulling element 1 out either leaves a hole every later index must dodge or forces a shift the container's own move-and-drop machinery cannot account for. We could have tracked the holes — mark a field or slot as moved-from and forbid its later use — but that is the per-element flow bookkeeping the entire design exists to avoid. So the rule forbids the fine-grained theft at the source and leaves the natural-grained operation intact: a whole `car` may be moved when it is itself a move-source; only reaching *into* a live host to steal a piece is denied.

Laid side by side, the five stop looking like a taste for blunt rules and start looking like what they are: five different doors onto the same room, each the minimal lock on one specific way a host and its value come apart — a guest outliving its host (§1.1, §1.7), a value sinking below a guest that still tracks it (§1.4), a value consumed on some paths but not others (§1.3), a value stolen from a host that still counts it (§1.2). None substitutes for another; each closes a gap the others leave open. That is the answer to the reader who finds them rigid and wonders where the slack is: there is none to give, because loosening any one is not a gentler version of the same safety but a specific, nameable crash let back in. This is [restriction as information](foundations.md#restriction-is-information-and-the-test-of-a-good-one) at the level of a single document — every rule that forbids a program is carrying a fact the compiler would otherwise have to prove — and [that the readable rule and the fast language coincide](foundations.md#strictness-is-the-performance-model) is the standing bet, not a coincidence.

The cost of buying safety this way is real, and it is not the false rejections — those the first chapter already owned. It is that the safety arrives as a *list* rather than a principle. A borrow checker derives every one of these cases from a single notion, a lifetime outliving a borrow; learn that idea and you hold all of it at once. Zane asks its reader to carry five separate rules instead, and nothing but a chapter like this one tells them the five are a set with no member removable. We think that is the right trade — five rules you can each check by eye against the code in front of you beat one proof you must trust a solver to have carried — but it is a genuine trade, and the chapter that pretends the rules are self-evidently a system, rather than a hard-won set each earning its place, is the chapter we had before this one.

## Where a guest may be rooted

The five rules of the previous chapter were each a lock on one way a host and its value come apart. Narrowing the guest source, over in [the memory story](memory.md#the-slot-that-could-not-be-pointed-at), turned out to change what two of those locks are guarding, and the adjustment is small enough to state precisely and worth stating because the reasoning is easy to get backwards.

The scope check ([§1.1](https://github.com/zane-lang/spec/blob/b10eaed/spec/lifetimes.md#11--assignment-uses-host-scope)) did not change at all — it still asks only whether the target's host is declared in the same or a higher lexical scope than the guest — but it now sits behind a prior question, because a source that is not a guest source never reaches the scope check in the first place. The visible effect is that the canonical illegal example is no longer the interesting one. `r = innerNode`, rejected for scope, used to be the rule's whole face; now the more common rejection is `r &Node = node`, refused before any scope is compared, and the example that still exercises the scope rule has to reach through a field to get there. That is a small loss of pedagogical clarity in exchange for a large one of exposure: the rule that used to be the only thing standing between a program and a dangling guest is now the second line of defence.

The rule that did change is the one governing returns ([§1.7](https://github.com/zane-lang/spec/blob/b10eaed/spec/lifetimes.md#17-returned--values-must-be-rooted-in-a-guest-parameter)). It used to say that a returned `&T` must be rooted in *a parameter*, which was the right rule when there was only one kind of reference parameter to be rooted in. With three, "a parameter" is no longer specific enough, and each of the other two fails for its own reason. A swallowing `T` parameter is a bare symbol in the call-site scope, and a bare symbol is not a guest source — so the returned guest could not have been minted in the first place. A `'T` borrow fails harder: the borrow ends when the call does, and a guest rooted in one would outlive the very access it was derived from. So the rule now names the guest parameter specifically. What makes this feel right rather than merely tighter is that the three modes each answer the question the rule is really asking — *may this outlive the call?* — and only one of them answers yes.

The same reasoning had to be pushed one step further than the rule's own text, and this is the part that is easy to miss. Refusing to return a `'T` parameter is pointless if you may instead return a guest minted from one of its **fields**: `this.weapon` on a borrowed subject would escape just as surely as `this` would, wrapped in one layer of indirection. So a field access rooted in a borrow is not a guest source either. We debated allowing it — the caller's object does outlive the call, so the guest would in fact be live — and rejected it on the grounds that "in fact live" is not the standard. The compiler would have to reason about the relative scopes of two objects across a call boundary to know it, which is the interprocedural analysis this whole document exists to avoid. A borrow that does not escape, with no exceptions and nothing to check, is worth more than a borrow that escapes safely under an argument only the compiler can follow.

Nothing else moved. The downgrade rule ([§1.6](https://github.com/zane-lang/spec/blob/b10eaed/spec/lifetimes.md#16-moved-symbols-downgrade-to--values-and-are-no-longer-movable)) still turns a moved-from symbol into a readable guest, and it is worth being clear that this is not in tension with the new source rule: the downgrade is something the language does to a slot, not a guest a program mints, and the reader never writes it. The signature-is-the-whole-contract rule ([§1.8](https://github.com/zane-lang/spec/blob/b10eaed/spec/lifetimes.md#18-passing-a-host-to-a-t-parameter-downgrades-it-to-a-guest)) simply grew a fourth entry — a verb may now *borrow* an argument as well as take a guest, relay, or consume — and the entry it grew is, satisfyingly, the one that leaves the caller in the strongest position: still the host, with the callee unable to keep anything.

The honest cost here is not a rejected program but a redistribution of where the reader's attention has to go. Before, a reference parameter's mode was visible in one bit — `&` or not — and the question "what happens to my object" had two answers. Now there are three signatures to read and three answers, and the difference between two of them (`&T` and `'T`) is invisible at the call site by design, because the whole point is that the call site should not have to care. The programmer who wants to know whether their host survives a call still reads exactly one thing, the signature; there is just more in it than there used to be.

## The root rule that got shorter

[The previous chapter](#where-a-guest-may-be-rooted) tightened the return rule and was pleased with itself for it. It had said, of the older and looser version, that "a parameter" was the right rule "when there was only one kind of reference parameter to be rooted in" — and with three kinds, it named the guest parameter specifically and gave each rejected mode its own reason. Both of those reasons have since been withdrawn, and the rule they were propping up went back to the sentence it started as.

The withdrawal is told in [the memory story](memory.md#the-ban-that-cost-more-than-the-question-it-closed): a bare symbol is a guest source again and the borrow mode is gone. Follow the consequences through §1.7 and both exclusions evaporate. A swallowing `T` parameter was excluded because it is a bare symbol and a bare symbol was not a source — but it is one now. A `'T` borrow was excluded because it expires with the call — but there is no `'T`.

What is interesting is that the rule which survives is not the old one restored by accident. It has a reason the old one never articulated, and the reason is stronger than either exclusion it replaces: **a parameter belongs to the call-site scope** ([§1.5](https://github.com/zane-lang/spec/blob/c36ef08/spec/lifetimes.md#15-parameters-belong-to-the-call-site)). Both modes have that property, which is why both are roots. A guest rooted in a parameter names something hosted in the very scope the returned value is landing in, so [the scope comparison](https://github.com/zane-lang/spec/blob/c36ef08/spec/lifetimes.md#11--assignment-uses-host-scope) has both declarations in front of it at the call site and rejects the cases that would dangle — including the one that looks alarming, where the argument was declared in a block nested below the binding that takes the return. Nothing about that check reaches across the call boundary, which is the property this document is organised around.

A local is still not a root, and the difference is that it is now excluded for the true reason rather than a proxy for it. `return value` on a body-scope local fails because that scope drains at the return, full stop — not because of anything about where a guest may be minted. When we were routing the rejection through guest sources we were using a source restriction to enforce a lifetime property, and it happened to catch this case; it is better stated as the lifetime property it always was.

The one line of the previous chapter that needs correcting rather than superseding is its account of §1.1. It reported that the scope check had become "the second line of defence", with the guest-source question in front of it catching the common case. That is no longer the shape: nearly every place is a guest source, so §1.1 is the front line again and does essentially all of the work. Its canonical illegal example goes back to being the one about scope, which is what the rule is actually about.

## The check that fired once, and the move that outran it

The previous chapter closed with §1.1 restored to the front line, doing "essentially all of the work." That was true of the case it was looking at — an `&` symbol, whose scope is fixed the moment it is declared — and it quietly assumed the same held for an `&` **field**, which it does not. A field's scope is its container's, and a container moves. So the comparison [§1.1](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/lifetimes.md#11--assignment-uses-host-scope) makes when the field is written can be falsified afterwards by a statement that never touches the field at all:

```zane
parked Car(outerHolder.engine)
{
    innerHolder Holder(Engine(Int(2)))
    arriving Car(innerHolder.engine)   // §1.1 satisfied: both in this block
    parked = arriving                  // a move, not an `&` assignment
}                                      // innerHolder dies; parked.engine names its storage
```

Every line passes. §1.1 fired at the construction and was right at the time. The move is checked by [§1.4](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/lifetimes.md#14-destination-scope-must-contain-or-match-source-scope), which compares the *value's* scopes and says nothing about what the value contains. Between them the two rules cover both directions a value can travel and neither looks at the guest riding inside it.

There is an asymmetry underneath that we had not noticed we were relying on. §1.4 exists to stop hosting from **sinking** into a nested scope. For a guest held inside the moved object the danger runs the other way — **raising** the container above what its guests name — and we had only ever constrained one of the two.

Our first instinct was to pin the value: an object holding an `&` may not be rehosted into a higher scope, full stop. That is decidable from the type alone, using the same transitive walk the value-downstream rule already performs, and it needs no new machinery. It is also wrong in the case that matters most. A parent pointer — `parent &Node` on a node stored in `root.children` — is the commonest reason anyone wants an `&` field at all, and pinning would forbid appending the child to the very tree its guest points at. A rule whose first casualty is the canonical use of the feature is not a conservative rule, it is a broken one.

That failure told us what the missing property was. What makes a parent pointer safe is not its scope but its *structure*: the guest names something in the same hosting tree as the object holding it, so the two move together and cannot come apart. [§1.2](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/lifetimes.md#12-move-sources-are-host-symbols-hosting-verb-results-or-variant-case-forms) already guarantees that, by refusing to let a subtree be prised out of its tree. So tree membership is stable under every operation the language has, where scope is stable under none of them.

We spent a while trying to make that the whole rule — an `&` may only name something inside its own tree — and it fails from the other side. A short-lived wrapper over something handed in, the sort of thing anyone writes without thinking, has no shared tree with what it points at:

```zane
Unit report(io std$IO) {
    terminal Terminal(io)   // io belongs to the call site and outlives the body
    terminal!print("hi")
    return Unit()
}
```

Perfectly safe, and a blanket tree rule forbids it. The resolution was to stop treating the two as rivals. **Tree membership is not an alternative to the scope comparison; it is the permission to move.** A guest that names something inside the value it rides in satisfies any destination, because it travels. A guest that does not is fine wherever it currently sits, and must be re-examined if the value is raised. Both readings live in §1.11, and neither had to displace the other.

The second realisation is the one that changed the shape of the fix, and it came from asking *when* the check should run. We had been trying to make the wiring-time check strong enough to survive everything that could happen later, which is why every version of it was either unsound or absurdly strict. It does not have to survive anything, because a raise is a statement the compiler can see. Check at the rise and the question of whether an earlier check has gone stale never arises: there is no earlier check to go stale.

That would have been the end of it, except for a program with no rise in it anywhere:

```zane
Unit setEngine(this Car, engine &Engine) mut { this.engine = engine; return Unit() }

Unit main(car &Car) {
    engine Engine()         // a local of main
    car!setEngine(engine)   // car names something above main
    return Unit()
}                           // engine dies; car.engine is left naming its storage
```

Nothing moves. The argument reaches a parameter in the call-site scope, and inside the body `this` and `engine` are both call-site scope, so every scope comparison in sight compares equals. And this is the shape [`memory.md` §2.9](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/memory.md#29-function-parameters-swallow-and-guest) had been holding up as the canonical thing an `&` parameter is *for*. What the callee cannot see is whether the caller's `engine` is hosted above or below the object `this` names — and it never can, because that is a fact about two of the caller's symbols, one frame away.

We tried hardest to fix this by narrowing where a guest may be **minted**. If only a guest could be a guest source — an `&T` parameter, `this`, a guest local rooted in one — then every guest would name something at the call-site scope or above, the highest any frame can rehost anything, and the whole class of problem would be structurally impossible. It is an elegant rule and we followed it a long way before noticing it has no base case. A parameter is fed by the caller's guest source, a guest local by another guest source; the recursion bottoms out only at a package constant, or at `this` — whose subject expression nothing checks, and cannot check, because `terminal!print("hi")` on a local you own has to work. The subject position is not a leak in that rule. It is the only place the language mints a guest at all, and a rule that closes it is a rule that deletes guests.

So the restriction had to land on the **store** rather than the source, and once it did the shape was forced. Both paths of an `&` store must begin with the same root symbol (§1.10). It is a syntactic comparison of two identifiers, it needs no scopes and no induction, and it holds however many frames a guest has travelled through, because it examines the two paths in front of it rather than their history. Everything reachable under one name is one tree, so a guest written through a name cannot outlive what that name reaches.

The cost is real and lands in one place: **a verb can no longer install a guest it was handed.** `setEngine` is gone, and the replacement takes hosting instead:

```zane
Unit installEngine(this Car, engine Engine) mut {
    this.spare = engine
    this.engine = this.spare   // both paths root at `this`
    return Unit()
}
```

That is a worse signature in one respect — the caller gives up its host where before it kept one — and a better one in another, because it says out loud what the old form concealed: an object that means to hold a reference to something for longer than a call had better be the thing that owns it. We debated softening the rule to admit the store when the destination roots at `this`, which would have kept `setEngine` alive, and dropped it on finding that a guest to a caller's local can be passed one hop further and stored from the other side. A rule that holds for one hop and not two is not a rule.

Two smaller things fell out that are worth recording. The ban in `memory.md` §2.9 on binding a swallowed parameter into `&` storage — which that section had flagged as "stated directly rather than derived" — is now an instance of the root rule, and stops being an orphan. And the returned-guest rule [§1.7](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/lifetimes.md#17-returned--values-must-be-rooted-in-a-parameter) turned out to have been right all along about a case it did not cover: a return that *carries* a guest is raised into the call-site scope on exactly the reasoning §1.7 gives for a return that *is* one, so §1.11 states it and §1.7 did not have to change.

What none of this touches is the other way a guest can be left naming nothing. Everything above is about a value **moving** away from what it points at. A host can also simply **die** while the guest is still there — an element removed from a container, a `#variant` slot changing case — and neither of those is a move, so no rule here reaches them. [`memory.md` §2.8.1](https://github.com/zane-lang/spec/blob/b486fd5f8c4d2ecdb14b8ef105394dc43aaf3bc6/spec/memory.md#281-a-guest-follows-the-object-an-overwritten-slot-carries-its-guests-forward) enumerates two fates for a hosted object, moved and overwritten, and says they "never compete, because an object cannot both leave and die in the same step." That is true, and the pair is not exhaustive: an overwrite leaves a successor occupant for the guest to carry forward to, and a removal leaves nothing. We are leaving that open deliberately rather than answering it here, because it is a different question with a different shape, and answering two at once is how the first version of this chapter got written three times.
