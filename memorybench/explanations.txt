# Benchmark result explanations.
#
# Authored from the maintainer-supplied full-suite run committed on 11 October
# 2026 on run-bench (80a440c). This is not a container pin. The JSON
# retains all 20 samples for every timed row; it records the workload
# configuration but no machine identifier or CPU-affinity setting. Compare
# rows within this run, not absolute times against an earlier pin.
# This pin measures native addresses and a contiguous fixed-size range
# followed by an unmapped guard range, so no fixed-region bump compares the
# frontier against the range's end inside timing. It includes the four-owner
# scope-frame variants in T1 and T3. Other fixed-region allocation rows
# retain per-object bumps as allocator-model workloads.
# These are reference C harness results, not compiled Zane programs.
#
# T10 sums node values during every allocator's timed teardown and checks
# that checksum against an untimed validation walk that also counts nodes.
# That validation walk warms the tree before timing. The arena row includes
# the same traversal plus the final bulk reset; it is not a reset-only timing.
#
# The median includes all twenty passes, including warm-up. The first pass is
# the slowest in 23 of the 52 timed rows. T1's per-object bump first pass is
# ~25.3x its median; T3's arena first pass is ~18.5x its median. Small
# differences and overlapping sample ranges do not establish a repeatable
# ordering. All interpretations below apply to this pin only, not every
# workload or machine. Changes to the model and measurement protocol also
# prevent attributing differences from older pins to a single design change.
#
# runbench.py renders each [Test N] block as that test's "Reading the result"
# note. Configuration and checked invariants live in benchmeta.py.
# After changing these notes, re-render without measuring:
#   python3 memorybench/runbench.py --from-file
# After pinning a new full-suite run, update these notes from that run first.

[Test 1]
Four-owner scope frames take ~13.0us, versus ~17.2us for the per-object
fixed bump, ~16.5us for the flat arena, ~274us for Pool and ~2.12ms for
malloc/free. The frame row is nominally ~1.32x faster than per-object bumps,
~1.27x faster than the arena, ~21.1x faster than Pool and ~163x faster
than malloc. Its sample range overlaps both bump rows. It reserves one
128-byte frame for every four owners and places them at fixed offsets, then
resets the frontier after the batch. The per-object bump and the arena both
bump once per object, and their medians differ by only ~4%, with overlapping
ranges; malloc and Pool also perform per-object frees inside timing. The
per-object bump's first pass (~435us) is ~25.3x its median.
Placement alone is modeled: scope records, object initialization and
first-touch faults in the fixed region are excluded. This is not a measurement
of complete scope entry and exit or whole-program compiler performance.

[Test 2]
Zane's row is an eliminated loop, not a measured zero-duration release.
zm_own_release is empty, so there is no per-object release work to time.
malloc (~954us) and Pool (~202us) return individual blocks to reusable
storage, at roughly 9.5ns and 2.0ns per object. Arena has no separate
per-object release row in this test; a bulk reset would be a different operation.

[Test 3]
Four-owner scope frames take ~299us, close to the per-object bump's
~296us: their medians differ by only ~1%, with overlapping sample ranges.
malloc takes ~4.21ms (~14.1x the frame row) and Pool ~1.22ms (~4.1x).
The frame row reserves 128 bytes for each 8/16/32/64-byte group, including
8 bytes of padding. Both fixed-bump rows and malloc/Pool also write size
metadata into the benchmark's pointer-size array and shuffle it inside timing.
The arena (~31.8us) writes a pointer array and resets without that shuffle,
so its ~9.4x lead over the frame row is not an allocator-only comparison.
Its first pass (~586us) is ~18.5x its median. As in T1, the frame row
excludes scope records, object initialization and fixed-region first-touch faults.

[Test 4]
Inline storage has the lowest median (~58.7us), followed by UList
(~62.6us), CChunked (~68.6us), sequential pointers (~101us) and shuffled
pointers (~170us). Sequential pointer access takes ~1.7x the inline median;
shuffling adds a nominal ~68% over sequential pointers. All five sample ranges
overlap, so these medians alone do not prove a repeatable ranking for every
layout. Iteration includes no allocation or freeing here: this compares
layouts and their scan loops, not allocator throughput.

[Test 5]
Zane's growing list takes ~211us, against ~248us for the realloc vector
(~1.18x), ~264us for CChunked (~1.25x), and ~833us for UList (~4.0x).
All four sample ranges overlap. Zane's first pass (~3.30ms) is ~15.7x its
median and the realloc vector's (~1.31ms) ~5.3x. Frontier growth avoids
copying while the block remains at the dynamic frontier inside its chunk;
oversized spans require relocation. These model timings do not imply the
same ordering for lists compiled by the Zane compiler.

[Test 6]
Native references take ~66.1us versus ~69.7us for direct pointers, a
nominal difference of ~5%, with overlapping sample ranges. In this C
model a reference stores the native pointer itself, and dereferencing it
returns that pointer directly: there is no segmented-offset decoding or
chunk-directory lookup. The small timing difference is not evidence of
an intrinsically faster access path. The benchmark checks that every
minted reference names its intended object.

[Test 7]
Pool (~1.713ms) and Zane (~1.723ms) are effectively tied; malloc takes
~2.007ms, about 16% longer than Zane's median. All three sample ranges
overlap, although malloc's minimum (~1.910ms) lies above both other medians.
The allocator-only gaps of T1 are much smaller once frame scans, updates
and object maintenance are part of the timed workload. This game-loop
model uses per-object fixed bumps rather than T1's four-owner scope frames.

[Test 8]
The arena (~5.339ms), Pool (~5.344ms) and serial Zane (~5.635ms) have
medians within ~5.5% of one another, with overlapping sample ranges.
malloc takes ~5.848ms, nominally ~4% longer than Zane, also overlapping.
This single run does not establish a stable ordering among the serial
variants. Both bump allocators retain dead particles' storage until the run
ends; Pool can recycle slots sooner. Arena performs the same serial updates
and a final bulk reset, never a reset between frames. The Zane work-stealing
variant (~73.1ms) is ~13.0x slower than serial Zane; for this workload the
measured parallel implementation does not amortize its per-frame scheduling costs.

[Test 9]
Refilling 50,000 objects takes Zane ~9.1us, malloc ~962us (~106x),
and Pool ~499us (~55x). Zane advances its frontier past dead storage
rather than reusing the released slots. Pool's samples range from ~68us
to ~593us and malloc's from ~664us to ~1.12ms, so those medians conceal
substantial variation. The large within-run separation survives that spread;
the exact speedup is specific to this measurement and this refill pattern.
Only refill is timed, not the initial allocation or checkerboard releases.

[Test 10]
Arena traversal plus bulk reset takes ~23.9us, Pool ~28.2us, Zane teardown
~28.7us and malloc ~60.9us (~2.1x Zane). The arena median is nominally
~17% below Zane, but their sample ranges overlap, as do Zane and Pool.
Every variant visits the same seeded 4,000-node tree, sums node values
during teardown and checks the checksum after timing. An untimed
validation walk counts nodes and warms the tree before every timed teardown.
Arena reclaims nodes and child lists together with one reset; Zane returns
dynamic child lists to size stacks, while node release is a no-op. These
figures describe traversal plus reclamation, not the reset operation alone.

[Test 11]
Pool (~1.722ms) and Zane (~1.732ms) differ by only ~0.6%, with
overlapping sample ranges. malloc (~1.872ms) is nominally ~8% above
Zane, also with overlapping ranges. Randomized scans, updates, list growth
and maintenance compress the allocator-only gaps seen elsewhere. This
workload gives no repeatable ordering for Zane versus Pool from a single run.

[Test 12]
The sequential shard scan takes ~82.3us, whereas the four-worker scan
is ~256us (~3.1x slower). Even best against best, ~162us concurrent
versus ~44.6us sequential is ~3.6x slower. The concurrent samples span
~162-504us. This small read-only workload does not benefit from this
parallel execution path, despite the persistent workers being pre-started
and warmed; it says nothing about larger workloads that amortize scheduling.

[Test 13]
Static-key boxed blocks take ~482us, runtime-key backing stores ~494us,
and frontier-only allocation ~97.5us. The two stack-based rows overlap
in their sample ranges, so the nominal static-key lead is not evidence
that static lookup is inherently faster. The frontier is ~4.9-5.1x faster
than these reusable-stack paths, but it consumes fresh storage each round.
The stack variants reuse returned blocks. Pool (~289us) has a lower median
than both Zane stack rows, with overlapping ranges; malloc (~1.69ms) is
clearly slower. The static-key first pass (~1.42ms) is ~2.9x its median.
The assertions verify exact-size, exact-alignment LIFO reuse and separation
of different stack keys, including tiny and weakly aligned blocks outside
the timed churn rows.

[Test 14]
Roaming-tree relocation (~25.7us) and deep value copy (~24.4us) are
effectively tied: their medians differ by ~5%, and their sample ranges
overlap. Fresh in-place construction takes ~15.2us, while malloc deep copy
takes ~107us (~4.4x the Zane value-copy median). Both relocation and
value copy walk all 8,191 nodes and allocate destinations; relocation also
returns old blocks to their stacks, but this run does not show a clear
timing penalty for that extra work. A move within the same scope remains
a handle copy and is not timed. The assertions also check settled overwrites
preserve the addresses seen by existing references.
