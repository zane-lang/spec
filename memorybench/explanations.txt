# Benchmark result explanations.
#
# Authored from the maintainer-supplied full-suite run committed on 11 October
# 2026 on run-memorybench (3ea8d04). This is not a container pin. The JSON
# retains all 20 samples for every timed row; it records the workload
# configuration but no machine identifier or CPU-affinity setting. Compare
# rows within this run, not absolute times against an earlier pin.
# This pin measures native addresses and a contiguous fixed-size range,
# including the four-owner scope-frame variants in T1 and T3. Other fixed-
# region allocation rows retain per-object bumps as allocator-model workloads.
# These are reference C harness results, not compiled Zane programs.
#
# T10 sums node values during every allocator's timed teardown and checks
# that checksum against an untimed validation walk that also counts nodes.
# That validation walk warms the tree before timing. The arena row includes
# the same traversal plus the final bulk reset; it is not a reset-only timing.
#
# The median includes all twenty passes, including warm-up. The first pass is
# the slowest in 21 of the 52 timed rows. T1's per-object bump first pass is
# ~47.2x its median; T3's arena first pass is ~10.8x its median. Small
# differences and overlapping sample ranges do not establish a repeatable
# ordering. All interpretations below apply to this pin only, not every
# workload or machine. Changes to the model and measurement protocol also
# prevent attributing differences from older pins to a single design change.
#
# runbench.py renders each [Test N] block as that test's "Reading the result"
# note. Configuration and checked invariants live in benchmeta.py.
# After changing these notes, re-render without measuring:
#   python3 memorybench/runbench.py --from-file
# After pinning a new full-suite run, update these notes from that run first.

[Test 1]
Four-owner scope frames take ~13.4us, versus ~26.3us for the per-object
fixed bump, ~15.1us for the flat arena, ~274us for Pool and ~2.31ms for
malloc/free. The frame row is nominally ~2.0x faster than per-object bumps,
~1.13x faster than the arena, ~20.5x faster than Pool and ~172x faster
than malloc. It reserves one 128-byte frame for every four owners and places
them at fixed offsets, then resets the frontier after the batch. The arena
bumps once per object; malloc and Pool also perform per-object frees inside
timing. The per-object bump's first pass (~1.24ms) is ~47.2x its median.
Placement alone is modeled: scope records, object initialization and
first-touch faults in the fixed region are excluded. This is not a measurement
of complete scope entry and exit or whole-program compiler performance.

[Test 2]
Zane's row is an eliminated loop, not a measured zero-duration release.
zm_own_release is empty, so there is no per-object release work to time.
malloc (~936us) and Pool (~221us) return individual blocks to reusable
storage, at roughly 9.4ns and 2.2ns per object. Arena has no separate
per-object release row in this test; a bulk reset would be a different operation.

[Test 3]
Four-owner scope frames take ~267us, close to the per-object bump's
~273us: their medians differ by only ~2%, with overlapping sample ranges.
malloc takes ~3.56ms (~13.3x the frame row) and Pool ~1.73ms (~6.5x).
The frame row reserves 128 bytes for each 8/16/32/64-byte group, including
8 bytes of padding. Both fixed-bump rows and malloc/Pool also write size
metadata into the benchmark's pointer-size array and shuffle it inside timing.
The arena (~28.7us) writes a pointer array and resets without that shuffle,
so its ~9.3x lead over the frame row is not an allocator-only comparison.
Its first pass (~310us) is ~10.8x its median. As in T1, the frame row
excludes scope records, object initialization and fixed-region first-touch faults.

[Test 4]
Inline storage has the lowest median (~50.6us), followed by CChunked
(~70.5us), UList (~81.3us), sequential pointers (~92.1us) and shuffled
pointers (~108us). Sequential pointer access takes ~1.8x the inline median;
shuffling adds a nominal ~17% over sequential pointers. The sample ranges
overlap, so these medians alone do not prove a repeatable ranking for every
layout. Iteration includes no allocation or freeing here: this compares
layouts and their scan loops, not allocator throughput.

[Test 5]
Zane's growing list takes ~203us, against ~368us for the realloc vector
(~1.8x), ~380us for CChunked (~1.9x), and ~924us for UList (~4.5x).
Zane's maximum (~491us) overlaps the other contiguous/chunked rows' ranges;
the realloc row reaches ~1.30ms. Frontier growth avoids copying while the
block remains at the dynamic frontier inside its chunk; oversized spans
require relocation. These model timings do not imply the same ordering
for lists compiled by the Zane compiler.

[Test 6]
Native references take ~68.4us versus ~69.9us for direct pointers, a
nominal difference of ~2.1%, with overlapping sample ranges. In this C
model a reference stores the native pointer itself, and dereferencing it
returns that pointer directly: there is no segmented-offset decoding or
chunk-directory lookup. The small timing difference is not evidence of
an intrinsically faster access path. The benchmark checks that every
minted reference names its intended object.

[Test 7]
Zane (~1.691ms) and Pool (~1.696ms) are effectively tied; malloc takes
~1.980ms, about 17% longer than Zane's median. Zane's sample range overlaps
both other rows. Pool's maximum (~1.762ms) is below malloc's minimum
(~1.881ms), so those two ranges do not overlap.
The allocator-only gaps of T1 are much smaller once frame scans, updates
and object maintenance are part of the timed workload. This game-loop
model uses per-object fixed bumps rather than T1's four-owner scope frames.

[Test 8]
Serial Zane (~5.489ms), Pool (~5.608ms) and the arena (~5.727ms) have
medians within ~4.3% of one another, with overlapping sample ranges.
malloc takes ~6.033ms, nominally ~10% longer than Zane. This single run
does not establish a stable ordering among the serial variants. Both bump
allocators retain dead particles' storage until the run ends; Pool can
recycle slots sooner. Arena performs the same serial updates and a final
bulk reset, never a reset between frames. The Zane work-stealing variant
(~72.1ms) is ~13.1x slower than serial Zane; for this workload the measured
parallel implementation does not amortize its per-frame scheduling costs.

[Test 9]
Refilling 50,000 objects takes Zane ~13.3us, malloc ~1.19ms (~89.6x),
and Pool ~596us (~45.0x). Zane advances its frontier past dead storage
rather than reusing the released slots. Pool's samples range from ~114us
to ~2.59ms and malloc's from ~647us to ~2.31ms, so those medians conceal
substantial variation. The large within-run separation survives that spread;
the exact speedup is specific to this measurement and this refill pattern.
Only refill is timed, not the initial allocation or checkerboard releases.

[Test 10]
Zane teardown takes ~27.7us, arena traversal plus bulk reset ~29.7us,
Pool ~30.9us and malloc ~65.5us (~2.4x Zane). The arena median is
nominally ~7% above Zane, but their sample ranges overlap, as do Zane
and Pool. Every variant visits the same seeded 4,000-node tree, sums node
values during teardown and checks the checksum after timing. An untimed
validation walk counts nodes and warms the tree before every timed teardown.
Arena reclaims nodes and child lists together with one reset; Zane returns
dynamic child lists to size stacks, while node release is a no-op. These
figures describe traversal plus reclamation, not the reset operation alone.

[Test 11]
Pool (~1.687ms) and Zane (~1.708ms) differ by only ~1.3%, with
overlapping sample ranges. malloc (~1.835ms) is nominally ~7% above
Zane, also with overlapping ranges. Randomized scans, updates, list growth
and maintenance compress the allocator-only gaps seen elsewhere. This
workload gives no repeatable ordering for Zane versus Pool from a single run.

[Test 12]
The sequential shard scan takes ~61.7us, whereas the four-worker scan
is ~282us (~4.6x slower). Even best against best, ~169us concurrent
versus ~56.5us sequential is ~3.0x slower. The concurrent samples span
~169-376us. This small read-only workload does not benefit from this
parallel execution path, despite the persistent workers being pre-started
and warmed; it says nothing about larger workloads that amortize scheduling.

[Test 13]
Static-key boxed blocks take ~308us, runtime-key backing stores ~252us,
and frontier-only allocation ~104us. The two stack-based rows overlap
in their sample ranges, so the nominal runtime-key lead is not evidence
that runtime lookup is inherently faster. The frontier is ~2.4-3.0x faster
than these reusable-stack paths, but it consumes fresh storage each round.
The stack variants reuse returned blocks. Pool (~184us) precedes both
Zane stack rows; malloc (~1.76ms) is clearly slower. The assertions verify
exact-size, exact-alignment LIFO reuse and separation of different stack keys,
including tiny and weakly aligned blocks outside the timed churn rows.

[Test 14]
Roaming-tree relocation (~24.9us) and deep value copy (~24.5us) are
effectively tied: their medians differ by ~1.4%, and their sample ranges
overlap. Fresh in-place construction takes ~18.4us, while malloc deep copy
takes ~116us (~4.7x the Zane value-copy median). Both relocation and
value copy walk all 8,191 nodes and allocate destinations; relocation also
returns old blocks to their stacks, but this run does not show a clear
timing penalty for that extra work. A move within the same scope remains
a handle copy and is not timed. The assertions also check settled overwrites
preserve the addresses seen by existing references.
