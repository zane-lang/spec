# Benchmark result explanations.
#
# Authored from the maintainer-supplied full-suite run committed on 9 October
# 2026, after adding the arena variants in T8 and T10. This is not a container
# pin. The JSON retains all 20 samples for every timed row; it records the
# workload configuration but no machine identifier or CPU-affinity setting.
# Compare rows within this run, not absolute times against an earlier pin.
# This pin measures the earlier segmented-offset representation and chunked
# fixed-size frontier. The harness now uses native addresses and a contiguous
# fixed-size range. These timings remain historical measurements; a new run
# from the maintainer's machine is needed to measure the updated model.
#
# T10 now sums node values during every allocator's timed teardown and checks
# that checksum against an untimed validation walk that also counts nodes.
# That validation walk warms the tree before timing. The previous pinned T10
# had neither step, so its times describe a different measurement protocol.
# The arena row includes the same traversal plus the final bulk reset; it is
# not a reset-only timing.
#
# The median includes all twenty passes, including warm-up. The first pass is
# the slowest in 16 of the 51 timed rows. T1's Zane first pass is ~16.8x its
# median; T3's arena first pass is ~12.4x its median. Small differences and
# overlapping sample ranges do not establish a repeatable ordering. All
# interpretations below apply to this pin only, not every workload or machine.
#
# runbench.py renders each [Test N] block as that test's "Reading the result"
# note. Configuration and checked invariants live in benchmeta.py.
# After changing these notes, re-render without measuring:
#   python3 memorybench/runbench.py --from-file
# After pinning a new full-suite run, update these notes from that run first.

[Test 1]
Zane's fixed-region bump (~32.2us) is ~60.6x faster than malloc/free
(~1.95ms) and ~6.9x faster than Pool (~223us) in this run. The flat arena
(~14.9us) is ~2.2x faster again. Zane release is a no-op; the arena reclaims
with a bulk reset, whereas malloc and Pool perform per-object frees inside
timing. Neither bump writes per-object metadata. Zane additionally maintains
a chunked frontier and checks chunk boundaries. Its first pass (~540us) is
~16.8x its median, so the median rather than that single pass is the figure
to read. These are allocator-model timings, not whole-program compiler results.

[Test 2]
Zane's row is an eliminated loop, not a measured zero-duration release.
zm_own_release is empty, so the compiler removes the random-order free loop.
malloc (~829us) and Pool (~178us) return individual blocks to reusable
storage, at roughly 8.3ns and 1.8ns per object. Arena has no separate
per-object release row in this test; a bulk reset would be a different operation.

[Test 3]
With mixed sizes, Zane takes ~252us, malloc ~3.79ms (~15.0x Zane),
Pool ~1.18ms (~4.7x), and the flat arena ~29.0us. Zane is still a pure
fixed-region bump without size classes or coalescing. The arena's first pass
(~358us) is ~12.4x its median. The large separations are clear within this
run, but their exact multiples should not be transferred to other machines.

[Test 4]
Inline storage (~62.4us), UList (~58.6us), and CChunked (~59.4us) are close;
the inline row has the lowest minimum (~49.2us), so the small median lead
of the chunked forms is not a robust ranking. Sequential pointer chasing
costs ~87.0us and shuffled pointer chasing ~119us, about 1.4x the
sequential pointer row. Iteration includes no allocation or freeing here:
this compares layouts and their scan loops, not allocator throughput.

[Test 5]
Zane's growing list takes ~203us, against ~243us for both the realloc
vector and CChunked, a nominal ~1.2x lead. UList is clearly slower at
~838us (~4.1x Zane). The realloc row's maximum (~1.36ms) is much larger
than its median. Frontier growth avoids copying while a block can remain
inside its chunk; oversized spans require relocation. The smaller gaps
need repeated runs before being treated as stable advantages.

[Test 6]
The segmented-offset rows (~64.2us with the directory cached and ~62.8us
reloaded) precede the direct-pointer row (~77.0us) in this run. Their best
passes (~63.6us and ~62.3us) also precede the direct row's ~68.2us.
This shows no slowdown for the offset representation in these scan loops;
it does not establish that offset resolution is intrinsically faster than
pointer dereferencing. The benchmark checks that every minted reference
resolves to its intended object.

[Test 7]
Zane (~1.733ms) and Pool (~1.738ms) are effectively tied; malloc is
~1.92ms, about 11% above Zane's median. Their sample ranges overlap.
The allocator-only gaps of T1 and T3 are much smaller once frame scans,
updates, and object maintenance are part of the timed workload.

[Test 8]
The new arena row (~5.565ms), Zane (~5.561ms), and Pool (~5.551ms)
are effectively tied: their medians span less than 0.3%, and their sample
ranges overlap. malloc takes ~6.08ms, nominally about 9% longer. This
run does not support the earlier pin's claim that Zane is last under this
churn workload. Both bump allocators retain dead particles' storage until
the run ends; Pool can recycle slots sooner, but that does not give a clear
speed advantage here. Arena performs the same serial updates and a final
bulk reset, never a reset between frames. The Zane work-stealing variant
(~61.3ms) is ~11.0x slower than serial Zane; for this workload the measured
parallel implementation does not amortize its per-frame scheduling costs.

[Test 9]
Refilling 50,000 objects takes Zane ~23.2us, malloc ~965us (~41.7x),
and Pool ~440us (~19.0x). Zane advances its frontier rather than searching
freed slots. Pool's samples range from ~83us to ~950us and malloc's from
~554us to ~2.14ms, so those medians conceal substantial variation. The
large within-run separation survives that spread; the exact speedup is
specific to this measurement and this refill pattern.

[Test 10]
The new arena traversal plus bulk reset takes ~23.2us, Zane ~24.9us,
Pool ~28.8us, and malloc ~62.3us. Arena is nominally ~7% faster than
Zane, but their sample ranges overlap; the clear separation is malloc at
~2.5x Zane. Every variant visits the same seeded 4,000-node tree, sums
node values during teardown, and checks the checksum after timing. An
untimed validation walk counts nodes and warms the tree before every timed
teardown. Arena reclaims nodes and child lists together with one reset;
Zane returns dynamic child lists to size stacks, while node release is a
no-op. These figures cannot be compared directly with the old T10 pin,
which did not include the checksum or the preceding validation walk.

[Test 11]
Zane (~1.63ms) and Pool (~1.64ms) are effectively tied. malloc (~1.78ms)
is nominally about 9% slower, with overlapping sample ranges. Randomized
scans, updates, list growth, and maintenance compress the allocator-only
gaps seen elsewhere. This workload gives no repeatable ordering for Zane
versus Pool from a single run.

[Test 12]
The sequential shard scan takes ~52.8us, whereas the four-worker scan
is ~204us (~3.9x slower). Even best against best, ~145us concurrent
versus ~52.6us sequential is ~2.8x slower. The concurrent samples span
~145-348us, so scheduling variability adds to the median's disadvantage.
This small read-only workload does not benefit from this parallel execution
path; it says nothing about larger workloads that can amortize the overhead.

[Test 13]
Static-key boxed blocks take ~292us, runtime-key backing stores ~257us,
and frontier-only allocation ~98.0us. The two stack-based rows overlap
in their sample ranges, so the nominal runtime-key lead is not evidence
that runtime lookup is inherently faster. The frontier is ~2.6-3.0x faster
than these reusable-stack paths, but it consumes fresh storage each round.
The stack variants reuse returned blocks. Pool (~186us) precedes both
Zane stack rows; malloc (~1.68ms) is clearly slower. The assertions verify
same-size, same-alignment reuse and separation of different stack keys.

[Test 14]
Roaming-tree relocation takes ~31.9us, deep-copying the value tree
~23.9us, fresh in-place construction ~20.3us, and malloc deep copy
~128us. Relocation is ~1.3x the value-copy median here; their sample
ranges do not overlap, unlike the tie in the earlier pin. Both operations
walk all 8,191 nodes and allocate destinations, but relocation also returns
old blocks to their stacks. That extra work is a plausible contributor to
the gap, not a causal conclusion proved by this timing alone. A move within
the same scope remains a handle copy and is not timed. The assertions also
check settled overwrites preserve the addresses seen by existing references.
